## D. 우리 기술은 무엇인가

### D-1. 한 줄 정의

> **가벼운 공개 OCR 모델(21MB) + 우리가 설계한 날짜 해석 규칙 + 어려운 사진에만 도는 예비 단계 + 시간 가드.** GPU·인터넷 없이 CPU 에서 사진 한 장 약 3초.

### D-2. 사용한 것

| 구성 | 내용 |
| --- | --- |
| 글자 위치 탐지 | PaddleOCR **PP-OCRv5 mobile det** (5MB, 공개 사전학습 모델) |
| 글자 인식 | PaddleOCR **en PP-OCRv5 mobile rec** (8MB, 공개 사전학습 모델) |
| 예비 인식기 | 위 인식기를 **우리 라벨로 파인튜닝**한 것 (8MB). 기본 인식기가 못 읽은 사진에만 사용 |
| 규칙 | 날짜 형식 정규화·후보 선택 규칙 (Python, 우리가 직접 작성) |
| 실행 환경 | Python 3.10, Jupyter 노트북 한 개(`predict.ipynb`), CPU 4코어, 오프라인 |
| 학습 | 구글 코랩 무료 T4 GPU, 비용 0원 |

### D-3. 우리 기술의 핵심 아이디어 6가지

1. **빠르게 읽기**: 사진을 640px 로 줄여 글자 위치를 한 번만 찾고, **큰 글자부터** 읽다가 날짜를 찾으면 작은 글씨는 건너뛴다. 8개씩 묶어 한 번에 읽는다.
2. **두 번 읽고 투표하기**: 날짜처럼 보이는 줄만 원본 해상도로 다시 읽어 첫 결과와 투표한다. 단, 다시 읽기는 **고치기만 하고 지우지는 못하게** 했다(이 규칙 하나로 45장 회복).
3. **규칙으로 소비기한 고르기**: 바코드(9자리 이상 숫자) 제거, "완전한 날짜"가 "숫자 나열"보다 항상 우선, 제조일과 같이 있으면 늦은 날짜, 연도는 2017~2031 만, 연월일 순서는 우리 라벨 통계로 결정.
4. **어려운 사진에만 예비 단계**: 옆에 날짜 줄이 더 있으면 그 주변만 다시 탐지 → 못 읽으면 도트 인쇄 전처리 → 그래도 못 읽으면 파인튜닝 인식기 → 작은 사진은 2배 확대. 쉬운 사진은 이 단계를 안 거쳐서 빠르다.
5. **시간 가드**: 최근 20장의 속도로 전체 시간을 예측해서, 늦을 것 같으면 예비 단계부터 스스로 끈다. 어떤 컴퓨터에서든 결과 파일은 반드시 나온다.
6. **모르면 모른다고 하기(NONE)**: 후보가 없으면 날짜를 지어내지 않는다. 연도만 안 보이면 `NONE-10-14` 처럼 그 칸만 비운다.

### D-4. 기술만큼 중요했던 "검증 방법"

| 방법 | 왜 |
| --- | --- |
| 3,352장 **전부 직접 라벨링**, 해석 규칙은 문서로 먼저 | 정답이 없으니 자부터 만듦. 라벨과 모델이 같은 규칙을 씀 |
| 500장 **봉인** | 개발에 안 쓴 시험지로 최종 점수를 잼 |
| **회복/퇴보를 따로** 셈 | 전체 점수가 올라도 맞던 사진을 많이 망가뜨리면 기각 |
| **정답도 의심** | 오답을 다시 보니 라벨이 틀린 게 23장, 그중 16장은 모델이 맞았음 |
| **직접 찍은 새 사진**으로 약점 측정 | 대회 사진 86% 가 실제 폰 사진에서도 나오는지 확인 → 52% |
| **모든 실험 기록** | `docs/실험_기록.md`, `results/` 에 예측 파일까지 남김 |

### D-5. 해 보고 버린 것 (심사에서 "왜 이건 안 했냐" 나올 때)

| 시도 | 결과 | 버린 이유 |
| --- | --- | --- |
| EasyOCR (처음 모델) | 39.1%, 장당 5.8초 | 느리고 부정확 |
| 파인튜닝 인식기를 1순위로 | +86 / −64 | 맞던 사진 64장을 망가뜨림 |
| 가짜 도트 글씨 3,000장 만들어 학습 | 76.8% | 진짜 글씨를 대충 읽게 됨 |
| 해상도 올리기 (5가지) | ±1%p, 시간 +30~50% | 원인이 해상도가 아니었음 |
| 사진 회전·탐지 기준 낮추기 | 회복 0장 | 엉뚱한 값만 나옴 |
| 한국어 인식기 2차 의견 | 최종 +7 / −2 | 시간이 늘어 제한 시간 여유를 택함(기본 끔, 켤 수는 있음) |

## E. 우리 팀의 강점 (자신 있게 말할 것)

1. **숫자로 말한다**: 모든 결정에 "몇 장을 얻고 몇 장을 잃었는지" 기록이 있다.
2. **정직하다**: 약점(폰 사진 52%, 위조를 못 막음, 이익을 금액으로 못 셈)을 먼저 공개한다.
3. **가볍다**: 21MB, GPU 0, 비용 0 — 바로 현장에 넣을 수 있는 크기.
4. **제한 조건을 설계로 풀었다**: 속도 때문에 모델을 바꿨고, 시간 가드로 0점 위험을 막았다.
5. **팀 전원이 데이터를 만들었다**: 3,352장 라벨 + 489장 직접 촬영.

# 2부. 발표 자료 이해하기

## 0. 30초 요약 (이것만은 외우기)

> 상품 뒷면 사진에서 **소비기한 날짜를 읽는 프로그램**을 만들었다. GPU 없는 컴퓨터에서 사진 한 장에 약 3초, 대회 사진으로는 **86%** 를 맞힌다.
> 이걸 **중고거래 앱**에 붙여서, 판매자가 식품 날짜를 찍으면 소비기한 칸을 자동으로 채워 주고 "167일 남음" 을 게시글에 보여 준다.
> 우리 설계의 핵심은 **확신이 없으면 "못 읽었다(NONE)" 고 말하는 것**. 틀린 날짜를 지어내지 않으니, 못 읽으면 판매자가 그냥 손으로 쓰면 된다.

## 1. 대회가 뭐였나

- **과제**: 상품 사진 3,352장이 주어지고, 사진마다 소비기한을 `2026-07-02` 형식으로 뽑아내는 것.
- **조건** (이게 중요 — 모든 설계가 여기서 나왔다):
  - 채점 컴퓨터는 **GPU 없는 4코어 CPU**, 인터넷 차단 → 무거운 AI 모델, ChatGPT 같은 외부 서비스 못 씀
  - **500장을 2,500초(약 41분) 안에** 끝내야 함. 넘으면 결과 파일이 안 나와 0점
  - 정답이 안 주어짐 → 정확도를 재려면 **정답을 우리가 직접 달아야** 했음
- **본선 채점 (100점, 전부 심사위원 평가)**: 설계 논리 25 · 정확성 20 · 속도 15 · 후처리·모델 근거 15 · 도메인·운영·비용 15 · 발표 10

## 2. 프로그램이 사진을 읽는 방법 (슬라이드 7번)

사람이 날짜를 찾는 과정과 같다고 설명하면 된다.

| 단계 | 사람으로 치면 | 실제로 하는 일 |
| --- | --- | --- |
| ① 탐지 | "글자가 어디 있지?" 훑어보기 | 사진을 작게 줄여서 글자가 있는 **위치(상자)** 를 찾는다. AI 모델 (PaddleOCR, 5MB) |
| ② 인식 | 글자 읽기 | 상자 안 글자를 읽는다. 큰 글자부터 읽고, 날짜를 찾으면 작은 글씨(성분표 등)는 건너뛴다. AI 모델 (8MB) |
| ③ 다시 읽기 | 헷갈리면 가까이 보기 | 날짜처럼 보이는 줄만 **원본 크기로 다시** 읽고 투표로 정한다 |
| ④ 해석 | "이게 소비기한 맞나?" 판단 | **규칙**으로 날짜 형식을 정리하고, 바코드·제조일 같은 다른 숫자를 걸러 소비기한을 고른다 |

- AI 모델은 ①②만 한다. "어느 게 소비기한인가" 판단은 사람이 만든 **규칙**이 한다 → 왜 그렇게 골랐는지 설명할 수 있다.
- 어려운 사진(점으로 찍힌 도트 인쇄 등)에만 추가 단계가 돈다. 쉬운 사진은 ①~④로 끝 → 빠르다.
- **시간 가드**: 처리가 늦어지면 스스로 단계를 줄여 제한 시간 안에 반드시 끝낸다. (실제로 9/28 에 PC 가 절전에 들어갔을 때 발동해서 끝까지 결과를 냈다.)

## 3. "소비기한을 다른 숫자와 어떻게 구분하나" (슬라이드 9번, 심사 20점 항목)

| 헷갈리는 숫자 | 예 | 규칙 |
| --- | --- | --- |
| 바코드·품목보고번호 | 20130628332176 | 9자리 이상 숫자는 날짜가 아니다 → 지움 |
| 영양성분표 | 78 7 5 31 | 점(.)이나 하이픈으로 구분된 "완전한 날짜"가 항상 이김 |
| 제조일 + 소비기한 | 25.06.26 / 26.06.25 | 둘 다 읽히면 **더 늦은 날짜** = 소비기한 |
| 연월일 순서 | 26.03.20 | 기본은 년.월.일. 말이 안 되면 일.월.년 (우리가 단 정답 통계로 정함) |
| 못 읽음 | — | 추측하지 않고 **NONE** |

## 4. 정확도를 어떻게 믿을 수 있나 (슬라이드 5번, 설계 논리 25점)

- **정답을 직접 달았다**: 5명이 3,352장 전부. 날짜 해석 규칙을 먼저 문서로 정하고 그대로 달았다.
- **시험지를 봉인했다**: 그중 500장은 따로 떼어 개발에 안 쓰고 **최종 점수 잴 때만** 썼다. → 86.2% 가 이 500장 점수. (컨닝 안 한 시험 점수라는 뜻)
- **점수가 올라도 버렸다**: 새 기능을 넣을 때 "새로 맞힌 사진"과 "원래 맞던 게 틀려진 사진"을 따로 셌다. 틀려진 게 많으면 전체 점수가 올라도 기각.
  - 대표 예: 파인튜닝(우리 데이터로 AI 재학습)은 +0.8%p 올랐지만 **64장을 새로 틀려서** 기각 (슬라이드 12번)

## 6. 도메인: 왜 중고거래인가 (슬라이드 16~19번, 15점)

**문제**: 명절이 끝나면 선물세트(스팸·참치·홍삼)가 중고거래로 쏟아진다. 당근은 식품을 올릴 때 소비기한을 적게 하지만 **판매자가 손으로 치고 아무도 확인하지 않는다.**

**우리 서비스 흐름**
1. 판매자가 앱 카메라로 날짜 부분을 찍는다
2. 서버가 읽고, **확신할 때만** 소비기한 칸을 채운다 (확신 없으면 빈칸)
3. 판매자가 날짜 확대 사진을 보며 확인하거나 고친다
4. 게시글에 "소비기한 2027-03-14 · 167일 남음" + 날짜 원본 사진 표시
5. 기한이 임박하면 "가격 내리거나 나눔 하세요" 알림, 지나면 게시글 자동 숨김

**핵심 논리 (이 문장이 발표의 결론과 이어진다)**
- 판매자가 마지막에 확인하니까, AI 가 틀려도 **한 번 고치면 끝**이다.
- 못 읽으면 빈칸이라 **지금보다 나빠지지 않는다.**
- 그래서 정확도는 "안전하냐"가 아니라 "**몇 %를 자동으로 채워 주냐**"를 정한다.

**왜 현실성이 있나**: 당근은 이미 건강기능식품 사진에서 **인증마크가 있는지를 OCR 로 확인**하고 있다. 우리는 같은 사진에서 **날짜 값**을 읽는 것 — 이미 도는 시스템에 기능 하나를 더하는 수준.

**1차 대상은 건강기능식품 카테고리**: 규칙이 명확(미개봉, 소비기한 이내만 판매 가능. 2025-05 전에는 6개월 이상 남아야 했음)하고 공개 통계가 있다(20개월 게시글 48만 건, 월 2.4만 건). 하루 800장 처리에 CPU 40분 → 비용은 거의 0.

**16번 슬라이드의 화면은 설계안(목업)이다**: 실제 앱을 만든 것이 아니다. 우리가 구현한 것은 날짜를 읽는 모델이고(14번이 실제 실행 화면), 16번 화면 속 날짜와 수치는 그 모델이 실제로 읽은 결과다. 질문이 나오면 그대로 말하면 된다.

**솔직히 인정하는 것**
- 판매자 폰 사진에서는 52% → 그래서 "확신할 때만 채우기"와 "판매자 확인" 구조
- 판매자가 날짜 스티커를 붙여 속이면 못 막는다 → 사기 방지가 아니라 **정직한 판매자를 돕는 장치**. 속이는 사람은 기존 신고·모니터링이 맡는다
- 인력 절감액은 부풀리지 않았다 → 소비기한 위반은 전체 위반의 5% 뿐이라서

## 8. 질문 받을 때 요령

- 답은 **결론 한 문장 → 숫자 하나 → "자세한 건 부록/보고서에"** 순서로 30초 안에.
- 모르면 지어내지 말고 "그건 측정하지 않았습니다. 가장 가까운 숫자는 ~입니다" (우리 발표 주제랑도 맞는 태도).
- 기술적으로 깊은 질문(모델 구조, 규칙 세부)은 **서현·병철에게 넘겨도 된다**: "그 부분은 구현한 팀원이 답하겠습니다."
- 자주 나올 질문 14개와 답은 `발표_대본.md` 의 "예상 질문과 답" 에 있다. 특히 이 셋은 꼭 읽기:
  1. "당근이 이미 OCR 하는데 새로운 게 뭐냐" → 당근은 마크 **유무**, 우리는 날짜 **값**과 해석
  2. "판매자가 확인하면 그냥 치는 거랑 뭐가 다르냐" → 신분증 스캔처럼 입력 편의 + 고친 값이 학습 데이터가 되어 계속 좋아짐
  3. "폰 사진 52% 로 되냐" → 확신할 때만 채우면 틀린 값 10%, 못 채운 건 빈칸이라 손해 없음
