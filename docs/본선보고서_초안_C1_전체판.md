## 1. 개괄

### 1-1. 핵심 접근 방식 요약

식품 포장 사진에서 소비기한을 읽는 문제를 **경량 사전학습 OCR + 날짜 해석 규칙 + 못 읽은 사진 전용 재시도**로 풀었다. 채점 조건(4코어 CPU, GPU 없음, 500장 2,500초, 인터넷 차단)이 설계를 정했다.

설계 전체에 걸친 원칙은 하나다. **틀릴 때 안전하게 틀리도록 만든다.**

| 층 | 원칙이 드러나는 곳 |
| --- | --- |
| 모델 | 확신이 없으면 날짜를 지어내지 않고 '미인식'으로 답한다. 시간이 모자라면 정확도를 내주고 완주를 지킨다 |
| 개발 방식 | 점수가 올라도 맞던 답을 흔드는 개선안은 버린다. 튜닝에 쓰지 않은 500장으로만 최종 수치를 말한다 |
| 활용 | 모델에게 날짜를 '읽히지' 않고 공장이 아는 정답과 '대조'하게 한다. 모델이 틀리면 사람이 한 번 더 보는 경보로 끝난다 |
| 기획 | 잡는 오류와 못 잡는 오류, 약한 경제성을 먼저 밝힌다 |

## 2. 데이터 구성 및 라벨링 전략

제공 데이터의 특징: 긴 변 700px 이하인 저해상도 사진이 33%, 제조일·소비기한 병기가 10%, 도트 인쇄와 각인이 많다. 이 세 무리가 오답의 대부분이다.

### 2-2. 라벨링 규칙 정의 및 수행 절차

**규칙을 먼저 문서로 정하고, 라벨링 도구와 모델이 같은 규칙을 쓰게 했다.** 모호한 표기는 팀의 후처리 규칙으로 채점한다는 운영진 확정에 맞춘 설계다.

| 구분 | 내용 |
| --- | --- |
| 사람이 하는 일 | 포장에 찍힌 **그대로** 입력(`2027.06.26`, `FEB/26/21`, `30 12 23`). 형식을 바꾸지 않는다 |
| 도구가 하는 일 (자동 규칙) | 연도가 뒤면 일/월/년, 2자리 세 개는 년/월/일 우선, 공백 구분은 일/월/년, 영문 월 처리, 연·월만 있으면 `YYYY-MM-NONE`, 월·일만 있으면 `NONE-MM-DD` |
| 사람이 판단하는 범위 | 두 날짜 병기는 늦은 날짜, 제조·포장일자만 있으면 `NONE`, 판독 불가, 애매함 등 태그 9종 |
| 수행 | 5명이 블록 단위로 분담, 해상도별로 섞어 무작위 배정. 파이프라인은 실행할 때마다 도구와 규칙이 같은지 자가검증 |

**정답 라벨도 검증했다.** 최종 구성 직전의 오답 446장을 사람이 전부 다시 봤다. 라벨 오류가 16장(오답의 3.6%)이었고, 그중 **11장은 모델이 맞고 사람이 틀린 것**이었다. 고친 값은 누가·언제·무엇을 바꿨는지 기록으로 남겼다. 점검자가 고친 18장 중 3장은 규칙 문서와 어긋나 다시 바로잡았다. 이 경험은 6절의 운영 설계(사람 확인도 기록하고 다시 검증한다)로 이어진다.

### 2-3. 전처리 내용

| 단계 | 내용 | 이유 |
| --- | --- | --- |
| 회전 보정, 디코딩 축소 | 촬영 방향대로 세우고 긴 변 2,000px 이하로 읽음 | 폰 사진의 디코딩 비용 절감 |
| 1차 읽기 축소 | 긴 변 640px, 후보가 없으면 1,024px | 해상도를 올려도 정확도 ±1%p 에 시간만 30~50% 증가. 480px 로 내리면 53.4 → 6.4% 로 붕괴 |
| 문자 필터 | 허용 문자 밖은 공백으로 치환 | 지우면 `2021(3)` 이 `20213` 으로 붙는다 |
| 도트 인쇄 전처리 | 후보가 없는 사진에만 침식·블러 후 다시 읽음 | 미인식의 주원인이 잉크젯 도트 인쇄. 500장 +17/−0 |
| 긴 숫자열 제거 | 9자리 이상 이어진 숫자는 해석 전에 제거 | 품목보고번호 앞 8자리가 완벽한 날짜로 읽힌다 |

## 3. 아키텍처 설계 논리

### 3-1. 전체 파이프라인 아키텍처 구조도

(그림 자리: `docs/img/architecture.png` — 최종 구성으로 다시 그릴 것)

```
사진
 ├─ ① 1차 읽기 (640px)   글자 위치 탐지 → 큰 글자부터 인식. 완전한 날짜를 찾으면 잔글씨 생략
 │      └ 후보 없음 → 1,024px 재시도 → 도트 인쇄 전처리 후 재시도
 ├─ ② 다시 읽기           날짜 후보 줄만 원본 해상도로 재인식 → 1차 결과와 다수결
 │      ├ [본선] 다시 읽은 결과가 1차 후보를 지우지 못하게 함
 │      ├ [본선] 일(日)이 한 자리로 읽히면 글자 상자를 넓혀 재인식
 │      └ [본선] 깨져 읽힌 날짜 모양 줄을 다시 읽어 둘 이상 일치할 때만 후보에 추가
 ├─ ③ [본선] 주변 재탐지   후보 줄 옆에 크기 비슷한 숫자 줄이 있을 때만 원본 해상도로 다시 탐지
 ├─ ④ 못 읽은 사진 전용    파인튜닝 인식기로 재시도 → [본선] 작은 사진은 2배 확대해 재시도
 ├─ ⑤ 해석·선택           형식 정규화 → 신뢰 등급 → 연도 범위 → 같은 등급 안에서 가장 늦은 날짜
 ├─ 시간 예산 가드         예상 소요가 예산을 넘으면 단계를 줄임. 결과 파일은 반드시 생성
 └─ 출력  YYYY-MM-DD / YYYY-MM-NONE / NONE-MM-DD / NONE
```

딥러닝 모델은 탐지기 1개와 인식기 2개(사전학습, 우리 라벨로 파인튜닝)이고 합쳐 약 21MB 다. 나머지는 전부 규칙이다.

### 3-2. 모듈별 설계 의도 및 기술 선택 이유

| 모듈 | 선택 | 근거 |
| --- | --- | --- |
| 탐지·인식 모델 | PP-OCRv5 mobile (탐지 5MB, 인식 8MB) | 처음 쓴 EasyOCR 은 4코어에서 장당 5.8초로 한도 초과. 교체 후 1.8초, 정확도 39.1 → 67.7% |
| 1차 읽기 640px + 재시도 | 어려운 사진에만 비용을 씀 | 전체 해상도를 올린 5개 구성이 모두 ±1%p, 시간 +30~50% |
| 다시 읽기 (다수결) | 후보 줄만, 탐지기 재실행 없이 | 탐지가 CPU 비용의 대부분. 다시 읽은 값이 1차 값을 덮어쓰던 초기 설계는 정확도 61.7% 대 유지 72.3% 로 폐기 |
| 주변 재탐지 | 조건을 만족하는 사진만 | 두 줄이 한 상자로 잡혀 한 줄만 읽히는 병기 대응. 조건 없이 모든 사진에 걸면 장당 6.2초 |
| 파인튜닝 인식기 | **못 읽은 사진에만** | 1순위로 쓰면 +38/−27, 다시 읽기 단계에 쓰면 +86/−64 로 맞던 답을 흔든다. 못 읽은 사진에만 쓰면 +7/−0 |
| 시간 예산 가드 | 3단계로 단계를 줄임 | 채점 서버 속도를 모른다. 시간 초과는 결과 파일이 없어 정확도까지 0점 |
| 미인식 정책 | 후보가 없으면 찍지 않음 | 틀린 날짜를 자신 있게 내는 것이 '모름'보다 비싼 오류 (6절) |

### 3-3. 후처리 규칙 설계

**(1) 소비기한과 다른 숫자의 구분**

| 헷갈리는 숫자 | 구분 방법 | 확인 |
| --- | --- | --- |
| 품목보고번호·바코드·제조번호 | 9자리 이상 숫자열 제거 | 시험 문자열 6종 모두 날짜로 읽히지 않음 |
| 전화번호 | 날짜 형식(자릿수·구분자·연도 범위)에 맞지 않아 걸러짐 | 시험한 10종 중 고객센터·지역번호 등 9종은 날짜로 읽히지 않음. 가운데가 연도처럼 보이는 휴대전화 번호 1종만 낮은 등급 후보가 됐고, 완전한 날짜가 있으면 등급 규칙이 무시 |
| 영양성분 숫자, 시각, 생산 라인 기호 | 신뢰 등급: 완전한 날짜가 있으면 공백 구분·6자리 압축 같은 약한 패턴은 보지 않음 | 등급 도입으로 500장 +15장. 시각·용량 8종 모두 날짜로 읽히지 않음 |
| 먼 미래 연도로 읽힌 잡음 | 연도 2017 ~ 2031 만 허용 | |
| 제조일자 | 같은 등급 안에서 가장 늦은 날짜 (소비기한 ≥ 제조일) | 병기 78.3% |
| 두 날짜에 걸친 가짜 날짜 (`2025.09.09 2026.09.08` 의 `09.09 2026`) | [본선] 구분자가 섞인 쪽을 버림 | +10/−0 |

**(2) 날짜 정규화**

| 표기 | 해석 |
| --- | --- |
| 4자리 연도가 앞 / 뒤 | 연월일 / 일월연 |
| 2자리 세 개 (`26.03.20`) | 년/월/일 우선. 불가능하거나 연도가 2028 이상이면 일/월/년 |
| 같은 사진에 `BBD` `EXP` `BEST BEFORE` 가 있음, 또는 공백 구분 | 일/월/년 |
| 미국식 | 일/월/년이 불가능할 때만 월/일/년 |
| 영문 월 (`FEB/26/21`, `22OCT2021`) | 월 위치를 확정하고 나머지를 자릿수로 판단 |
| 연·월만 / 월·일만 | `YYYY-MM-NONE` / `NONE-MM-DD` |
| 잘못 읽힌 글자 | `2O27` → `2027`, 도트 조각 사이 공백 제거, 구분자 하나 빠짐 허용 |
| [본선] 콜론 구분, 날짜 뒤에 붙은 숫자(`21.02.10011`), 연·월 사이 구분자 빠짐(`202104.19`) | 각각 +6/−0, +16/−1, +8/−1 |

**(3) 미인식 `NONE` 기준**: 후보가 0개면 `NONE`. 자주 나오는 날짜를 찍지 않는다. 연도나 일만 없으면 그 칸만 `NONE` 으로 둔다. 시간 예산 가드의 마지막 단계에서 남은 사진도 `NONE` 으로 채워 결과 파일을 만든다.

## 6. 도메인 활용 및 운영 기획

### 6-1. 적용 도메인 및 도입 대상 기업/산업 정의

**중소 식품공장의 출하 전 '날짜 인쇄 확인'.**

| 항목 | 내용 |
| --- | --- |
| 문제 | 날짜 인쇄기는 가동 전에 입력한 값을 다음 확인 전까지 모든 제품에 찍는다. 숫자 하나의 설정 실수가 배치 전체의 회수로 이어진다 |
| 사례 | 국내 깐땅콩(2026)·단백질 보충제(2019), 영국 Tesco·Pieminister(2024~2025), 일본 통조림 연도 오류. 대부분 날짜가 늘어나는 방향이라 안전 문제 |
| 빈칸 | HACCP 표준 문서(가이드라인 6종, 표준기준서 2025·2016)는 날짜를 '표시사항 준수' 한 줄로만 적는다. 확인 주기·방법·조치·기록 서식이 없고, 평가도 날짜가 찍혀 있는지만 본다 |
| 대상 | 인라인 비전 검사 장비가 없는 소규모 해썹 업체. 해썹 적용 기업의 약 81% |
| 대상이 아닌 곳 | 인쇄기를 전산과 연동하거나 인라인 검사를 쓰는 대형 업체 |

**읽기가 아니라 대조.** 공장은 정답(제조일 + 품목별 소비기한 일수)을 이미 안다. 모델에게 백지 시험이 아니라 채점을 시킨다. 업계는 이를 읽기(OCR)와 구분해 대조(OCV)라 부른다.

| | 모델 결과 = 기대값 | 모델 결과 ≠ 기대값, 또는 미인식 |
| --- | --- | --- |
| **인쇄가 맞음** | 통과 | 헛경보 → 사람이 한 번 더 확인 |
| **인쇄가 틀림** | **놓침** — 모델이 틀린 인쇄를 하필 기대값으로 읽은 경우만 | 정상 탐지 → 출하 보류 |

모델의 실수는 대부분 헛경보로 간다. 그래서 이 도메인에서는 모델을 사람의 판독 정확도와 비교하지 않는다.

**놓칠 확률을 실측했다 (오류 주입 실험).** 봉인 500장 중 라벨이 완전한 날짜인 474장에서, 실제 인쇄를 라벨로 두고 기대값을 일부러 어긋나게 만들어 모델의 답이 그 기대값과 같아지는 비율을 셌다.

| 어긋남 유형 | 일 ±1 | 일 ±2 | 1주 | 월 ±1 | 연 +1 | 연 −1 | 일·월 뒤바뀜 | 평균 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 놓침 (한 장당) | 0.2 ~ 0.4% | 0 ~ 0.4% | 0.2% | 0% | 0.2% | **0.6%** | 0% | **0.23%** |

- 판정용 2,680장에서는 평균 0.10% 였다. 역산으로 잡았던 최악 상한(완전한 날짜로 틀린 비율 8.4%)보다 수십 배 작다.
- 가장 나쁜 유형(연 −1)은 병기 제품에서 모델이 제조일을 읽는 경우다. 실제 회수 사례에 많은 '연도가 1년 늘어난 오인쇄'와 같은 방향이므로, 병기 품목은 **두 날짜를 모두 대조**한다.
- "기대값이 후보 목록 안에 있으면 통과"로 바꾸면 통과율은 0.6%p 오르지만 연 −1 놓침이 0.6 → 2.3% 로 늘어 채택하지 않았다.
- 표본이 작아 유형별 값은 1~3장 차이다.

### 6-2. 운영 아키텍처 설계 (서버 / 온디바이스)

**구성**: 작업자 폰(촬영) + 공장 내부 PC 1대(판독·판정·기록). 서버·클라우드·인터넷 연결이 필요 없다. 모델 21MB, CPU 전용, 오프라인 동작을 검증했다.

```
폰 촬영(고정 거치대) → 해상도·흐림 검사(미달이면 바로 재촬영) → 사내망 → 내부 PC 판독
   → 기대값과 대조 → 판정 → 로컬 기록(사진·시각·작업자·품목·기대값·판독값·판정·모델 버전) → 일일 리포트
```

| 항목 | 설계 | 근거 |
| --- | --- | --- |
| 기대값 | 촬영 시점의 **시스템 날짜** + 품목 마스터의 소비기한 일수 | 제조일을 사람 입력이 아닌 시스템 날짜로 잡아, 인쇄기 설정과 기대값이 같은 입력 실수를 공유하지 않게 함 |
| 품목 마스터 | HACCP 제품설명서의 기한 항목을 옮기고 품목제조보고서와 대조, 등록·승인 2인 | 새로 만드는 자료가 아니라 이미 관리하는 문서 |
| 언제 찍나 | 가동 시작, 품목 전환, 인쇄기 수정 직후, 자정 이후 + 정기 | 오류가 몰리는 순간이 예측 가능. 정기 촬영은 기존 금속검출기 점검 시점에 같은 사람이 |
| 저해상도 약점 | 거치대로 거리 고정, 기준 미달 사진은 받지 않음 | 저해상도 83.7% 대 중해상도 89.5% |
| 최종 판단 | 출하 여부는 항상 사람 | 시스템은 두 번째 눈이자 기록 장치 |

**판정 규칙 — '같은 틀린 값'을 확인한다.** 진짜 오인쇄는 그 구간의 모든 제품에 같은 틀린 날짜가 찍히고, 모델의 판독 오류는 제품마다 다르게 나온다.

1. 첫 장이 기대값과 같으면 통과.
2. 다르면 바로 멈추지 않고 **다른 제품 두 장**을 더 찍는다. 세 장 중 두 장 이상이 기대값이면 통과.
3. 여러 장이 기대값이 아닌 **같은 값**으로 읽히면 강한 경보: 마지막 통과 이후 생산분 출하 보류.
4. 값이 제각각이거나 미인식이면 약한 경보: 사람이 실물 확인.

| 규칙 | 정상 인쇄에서 사람 확인 | 하루 확인 (점검 20회) | 놓침 확률 | 점검당 추가 촬영 |
| --- | --- | --- | --- | --- |
| 한 장 판정 | 13.8% | 약 2.8건 | 0.23% | 없음 |
| 세 장 중 두 장 | **약 3.5%** `[가정]` | **약 0.7건** | 거의 같음 | 0.28장 |

`[가정]` 사진 간 판독 오류가 서로 독립이라고 둔 계산. 같은 제품을 여러 장 찍는 실험으로 확인한다(7절).

**잡는 오류와 못 잡는 오류**

| 구분 | 오류 유형 | 대응 |
| --- | --- | --- |
| 잡음 | 인쇄기 입력 실수, 품목 전환 뒤 이전 설정 유지, 교대·자정 뒤 날짜 미갱신, 인쇄기 시계 오류 | 인쇄 결과가 기대값과 다름 |
| 보완 후 잡음 | 생산지시 제조일 오입력 | 제조일을 시스템 날짜로 산출 |
| **못 잡음** | 품목 마스터의 소비기한 일수 오등록 | 기대값도 함께 틀린다. 2인 승인으로 예방하고, 변경 이력으로 영향 기간을 특정 |
| 추가 검사 | 기대값과 무관한 정합성 | 병기 품목은 '소비기한 − 제조일 = 등록 일수' 확인, 촬영일보다 이른 소비기한은 무조건 보류 |

우리가 주장하는 독립은 자료의 독립이 아니라 **판독 경로의 독립**이다. 입력한 값이 아니라 실제로 찍힌 결과를 다시 읽는다.

**경보 피로 대비**: 확인 화면에 판독값과 기대값을 숨기고 작업자가 실물 날짜를 직접 입력한다. 주 1회 틀린 날짜 스티커를 붙인 시험 제품으로 시스템과 작업자를 함께 점검한다(금속검출기 시편 점검과 같은 절차). 품목별 헛경보율을 지표로 둔다.

### 6-3. 예상 운영 비용 산출

라인 1개, 하루 점검 20회, 연 250일 기준.

| 항목 | 계산 | 값 |
| --- | --- | --- |
| 서버·클라우드·라이선스·학습비 | 오프라인 자체 모델, 무료 학습 | 0원 |
| 하드웨어 | 기존 폰과 PC. 거치대는 별도 | 거치대 가격 확인 필요 |
| 하루 연산 | (20장 + 추가 촬영 5.5장) × 장당 4초 | 약 100초. PC 1대가 시간당 약 900장 처리 |
| 추가 인건비 — 촬영을 따로 할 때 | (촬영 20회 × 15초 + 확인 2.8건 × 30초) × 최저시급 10,320원 | 연 약 27만 원 `[가정]` |
| 추가 인건비 — 기존 점검에 묶고 세 장 규칙 | (추가 촬영 5.5장 × 15초 + 확인 0.7건 × 30초) × 최저시급 | **연 약 7.5만 원** `[가정]` |
| 사진 저장 | 장당 3MB | 연 약 20GB |

`[가정]` 촬영 15초·확인 30초는 실측 전 값이고, 인건비는 최저임금 기준 하한이다. 설치·교육·품목 마스터 관리 시간은 포함하지 않았다.

### 6-4. 비즈니스 손실 절감 효과 및 ROI 기획

**계산을 먼저 공개한다.** 오류 발생률을 모르는 채로 ROI 를 한 숫자로 말하면 지어낸 숫자가 된다. 그래서 손익분기로 제시한다.

> 연간 이익 = (연간 오인쇄 발생 건수) × (1건당 손실) × (탐지 확률) − 연간 비용

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 업체당 연 발생률 (관대한 상한) | 약 0.0012 | 표시 위반 회수 67건 / 5.5년 ÷ 해썹 업체 10,101곳. 날짜 오류만 세면 더 작다 |
| 탐지 확률 | 약 99.8% | 놓침 0.23% (6-1절) |
| 손익분기 1건당 손실 — 촬영을 따로 할 때 | 약 2.3억 원 | 27만 원 ÷ 0.0012 |
| 손익분기 1건당 손실 — 기존 점검에 묶을 때 | 약 6,300만 원 | 7.5만 원 ÷ 0.0012 |

**기대 손실만으로는 소규모 업체 한 곳의 도입 근거가 약하다.** 이것을 숨기지 않고, 가치를 세 가지로 설명한다.

| 가치 | 내용 |
| --- | --- |
| 생존 위험 대비 | 배치 회수와 반복 위반 시 품목제조정지·영업정지는 소규모 업체에게 평균이 아니라 존속의 문제다. 이를 연 10만 원 안팎의 고정비로 대비한다 |
| 회수 범위 특정 | 시각별 판정 기록이 있으면 오류가 뒤늦게 드러나도(품목 마스터 오등록 포함) 언제부터 언제까지인지 특정해 회수 범위를 좁힌다 |
| 검증 운영 부담 | 소규모 업체의 HACCP 평가 지적 1위가 검증관리(27.3%)다. 자동 기록이 이 부담을 덜 수 있다 (정황 근거) |

**촬영 주기**: 자주 찍으면 인건비가 늘고 드물게 찍으면 오류 뒤 생산분이 커진다. 하루 비용을 최소로 하는 주기는 T* = √(2 × 1회 촬영 비용 ÷ (시간당 오류 발생률 × 시간당 생산량 × 1개당 손실)) 이다. 생산량이 많거나 제품이 비쌀수록 자주 찍는다. 여기에 오류가 몰리는 순간의 이벤트 촬영을 얹는다.
