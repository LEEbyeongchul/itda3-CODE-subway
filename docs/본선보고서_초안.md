## 1. 개괄

### 1-1. 핵심 접근 방식 요약

식품 포장 사진에서 소비기한을 읽는 문제를 **"경량 사전학습 OCR + 도메인 규칙 후처리 + 두 겹 폴백"** 으로 풀었다. 채점 조건(4코어 CPU, GPU 없음, 500장 2,500초, 오프라인)이 설계를 결정했다.

1. **탐지·인식은 PaddleOCR PP-OCRv5 mobile** (탐지 5MB, 인식 8MB). 처음 쓰던 EasyOCR(CRAFT + english_g2)은 4코어에서 장당 5.8초로 시간 한도를 넘겼고, 교체 후 1.8초로 줄면서 정확도도 39.1% → 67.7%(133장)로 올랐다.
2. **후처리 규칙은 오답을 보고 하나씩.** 정규식 4단계 신뢰 등급, 2자리 연도 해석 규칙, 긴 숫자열(품목보고번호·바코드) 제거, 연도 범위 검증, 같은 등급 안에서 가장 늦은 날짜 선택. 라벨링 도구와 파이프라인이 **같은 규칙**을 쓴다.
3. **두 겹 폴백.** 후보가 없을 때만 도트매트릭스 전처리(침식·블러)로 재시도하고, 그래도 없으면 우리 라벨로 파인튜닝한 인식기로 재시도한다. 파인튜닝 인식기를 1순위로 두면 퇴보가 생겨 폴백으로만 쓴다.
4. **완주 보장.** 최근 20장 속도로 총 소요를 예측해 예산을 넘길 것 같으면 경량 단계로 내려간다. 타임아웃이면 CSV 가 안 나와 정확도까지 0점이기 때문이다.
5. **측정 프로토콜을 먼저 세웠다.** 3,352장 전수를 팀이 직접 라벨링하고, 500장(블록 1~5)은 봉인해 튜닝에 쓰지 않았다. 규칙 채택은 나머지 2,852장에서 회복·퇴보를 따로 세어 판정했다.

본선에서는 예선 동결본의 오답 603장을 "정답이 파이프라인 어느 단계까지 살아 있었나"로 진단해 4단계(선택 실패·2패스 삭제·오독·미검출)로 나누고, 단계별로 담당을 나눠 고도화했다.

### 2-2. 라벨링 규칙 정의 및 수행 절차

**규칙을 먼저 정의하고, 라벨과 모델이 같은 규칙을 쓰게 했다.** 운영진 확정 "모호한 값은 팀의 후처리 규칙으로 채점" 에 대응한 설계다.

- **정본**: `docs/날짜_해석_규칙.md`. 라벨링 도구 `notebooks/label.py` 의 `normalize()` 와 파이프라인의 `parse_dates()` 가 같은 규칙을 구현하고, 파이프라인은 셀 실행 시 자가검증(assert)으로 정합을 확인한다.
- **입력 원칙**: 포장에 찍힌 **그대로** 입력(`2027.06.26`, `FEB/26/21`, `30 12 23`). 도구가 규칙대로 정규화한다. 표기 형식 자체가 분석 데이터이므로 라벨러가 형식을 바꾸지 않는다.
- **자동 정규화 룰(도구)**: 연도가 뒤면 일/월/년, 2자리 연도 3숫자는 년/월/일 우선(연도 범위 밖이거나 2028 이상이면 일/월/년), 공백 구분은 일/월/년, 영문 월 이름 처리, 연·월만이면 `YYYY-MM-NONE`, 월·일만이면 `NONE-MM-DD`.
- **수동 판단 범위(라벨러)**: 병기는 늦은 날짜 + 태그 `2`, 제조·포장일자만 있으면 `NONE`(운영진 확정 #15), 유럽식이 확실하면 `d`, 판독 불가 `s`, 애매하면 `?`. 태그 9종(`2 d r t b e n s ?`)으로 사진 특성을 함께 기록해 오류 분석에 쓴다.
- **수행 절차**: 5명이 블록 단위로 분담(1·2차 각 100장 × 10블록, 3차 470장 × 5블록). 해상도 층(small·mid·large)을 섞어 무작위 배정. 도구는 이어하기·되돌리기(Ctrl+Z)·화면 회전을 지원. 블록당 파일이 달라 git 충돌 없음.
- **품질 관리**: 오답 84장 육안 검토로 라벨 오류 7장 수정, 규칙 변경(제조일자만 → NONE) 7장 수정. `?` 태그는 모아서 재검토. 파인튜닝 크롭 검수에서 편집거리 3 크롭은 다른 줄과 잘못 짝지어진 것이 10% 남짓 섞여 제외.
- **증빙**: 저장소 루트 `custom_data/` 에 라벨 정본 `labels_all.csv`(3,352행) + 블록별 CSV + 검토 자료 + 규칙 문서 + 도구.

## 3. 아키텍처 설계 논리

### 3-1. 전체 파이프라인 아키텍처 구조도

그림: `docs/img/architecture.png` (⏳ 본선 최종 구성으로 재생성 필요 — 2패스 유지 규칙·콜론·확장 재인식, 병철 재탐지 채택 여부 반영).

```
원본 이미지
 ├─ ⓪ EXIF 보정, 디코딩 축소(≤2000px)
 ├─ ① 1패스 (640px)
 │    ├─ 탐지  PP-OCRv5 mobile det          텍스트 박스 (4스레드 약 300ms)
 │    ├─ 인식  en_PP-OCRv5 mobile rec       글자 크기순 8개 배치. 연도 포함 날짜를 찾으면 그 높이 60% 미만 박스 생략
 │    ├─ 후보 없으면 1024px 로 한 번 더 (사다리)
 │    └─ 그래도 없으면 도트매트릭스 폴백 (침식·블러·팽창 → 같은 사다리)
 ├─ ② 2패스  후보 줄의 단어 박스만 원본·1024px 에서 크롭 재인식 → 1패스와 다수결
 │    └─ [본선] 유지 규칙: 2패스에 같은 연·월 후보가 없으면 1패스 후보를 지우지 않는다
 │    └─ [본선] 한 자리 일 확장 재인식: 일이 한 자리로 읽히면 박스를 오른쪽으로 넓혀 다시 읽는다
 ├─ ③ 파인튜닝 폴백  ①·② 전부 NONE 이면 우리 라벨로 파인튜닝한 인식기로 ①·② 재시도
 ├─ ④ 후처리  오독 복원 → 정규식 4단계 신뢰 등급 → 연도 2017~2031 → 긴 숫자열 제거 → 등급 안에서 가장 늦은 날짜
 ├─ 시간 예산 가드  최근 20장 속도로 총 소요 예측 → 초과 예상 시 경량 단계(사다리 생략 → 2패스·폴백 생략 → NONE)
 └─ 출력  YYYY-MM-DD / NONE-MM-DD / YYYY-MM-NONE / NONE
```

딥러닝 모델은 탐지기 1개, 인식기 2개(사전학습·파인튜닝). 나머지는 전부 규칙이다.

### 3-2. 모듈별 설계 의도 및 기술 선택 이유

| 모듈 | 선택 | 왜 |
| --- | --- | --- |
| 탐지기 | PP-OCRv5 mobile det (5MB) | CRAFT(VGG16)는 4코어 장당 5.8초로 한도 초과. 교체로 0.3초. YOLO 전용 탐지기는 박스 라벨이 0장이라 학습 불가였고, 탐지기 교체만으로 속도·정확도가 함께 해결됨 |

| 1패스 축소 640px + 사다리 | 어려운 장에만 비용 | 해상도 상향 5구성 전부 ±1%p, 시간 +30~50%. 미검출은 해상도가 아니라 인식 문제 |
| 조기 종료 | 연도 포함 날짜를 찾으면 작은 글씨 생략 | 영양성분표 잔글씨 인식이 시간의 큰 몫. 해제 실험 +2/−1, 시간 +2% → 유지 |
| 2패스 다수결 | 후보 줄만 원본·1024px 재인식, 검출기 재실행 없음 | 검출기가 CPU 비용의 대부분. 500장 +7/−0. 2패스가 1패스를 덮어쓰게 했던 초기 설계는 덮어쓴 답 정확도 61.7% vs 유지 72.3% 로 폐기 |
| 도트매트릭스 폴백 | 후보 없을 때만 침식·블러 | 미검출을 육안 확인하니 대부분 잉크젯 도트. 후보 없는 6~15% 장에만 비용. 500장 +17/−0 |
| 파인튜닝 인식기 = 폴백 | 사전학습 1순위, NONE 일 때만 파인튜닝 | 파인튜닝 단독 +38/−27, 1순위로 두면 규칙이 맞히던 25장을 새로 틀림. "둘이 서로 다른 데서 틀린다"를 이용해 폴백으로만 쓰면 +7/−0 |
| 시간 예산 가드 | 3단계 경량화 | 채점 서버 속도를 모르는 상태에서 타임아웃(=0점)을 구조적으로 차단. 예산 100초 강제 발동 시험으로 단계 상승 사슬·CSV 생성 확인 |
| NONE 정책 | 후보 없으면 찍지 않음 | 정답에 NONE 이 실제로 존재(연도 없음 2.5%, 일 없음 3.3%). 운영 관점에서 "모르면 사람에게" 가 맞음 |

### 3-3. 후처리 규칙 설계

**(1) 소비기한과 다른 숫자의 구분**

| 잡음 | 구분 방법 |
| --- | --- |
| 품목보고번호·바코드 (`20130628332176`) | 9자리 이상 연속 숫자열은 파싱 전 제거 |
| 영양성분표 숫자열, 로트·시각 | 패턴 신뢰 등급. 완전한 날짜(등급 1)가 있으면 공백 구분·6자리 압축(등급 2~3)·부분 날짜는 보지 않음. 등급 도입으로 500장 +15장 |
| 미래 연도 잡음 (`2029-08-14`) | 연도 허용 범위 2017~2031(라벨 실측 최소 2017). 2자리 연도는 2028 이상이면 일/월/년으로 재해석 |
| 제조일자 vs 소비기한 | 같은 등급 후보 중 **가장 늦은 날짜**(소비기한 ≥ 유통기한 ≥ 제조일, 운영진 확정 #12). 제조·포장일자만 있는 사진(0.2%)은 라벨을 NONE 으로 |
| 같은 글자의 이중 해석 (`2025.07.12 2026.07.11` 의 `12 2026.07`) | 범위 가림 규칙을 실험했으나 +10/−5 로 대칭 결함 → 기각. 알려진 한계로 기록 |

**(3) 미인식 `NONE` 처리 기준**

- 후보 0개 → `NONE`. 사전확률 날짜를 찍지 않는다.
- 연도 없음 → `NONE-MM-DD`, 일 없음 → `YYYY-MM-NONE` (필드별 부분점수).
- 시간 예산 가드 3단계에서 남은 장은 `NONE` (CSV 는 반드시 생성).
- 운영 관점: 신뢰도 임계값 하나로 NONE 비율을 조절해 "확신 없으면 사람에게" 로 운용 가능. 답한 것의 정밀도 86%.

**(4) 본선에서 추가한 2패스 규칙** — 예선 오답 진단에서 "1패스는 맞게 읽었는데 2패스 재인식이 정답을 덮어쓴" 111장을 발견했다.

| 규칙 | 내용 | 판정용 2,852장 |
| --- | --- | --- |
| 유지 규칙 (`ITDA_P2_KEEP`) | 2패스 출력에 같은 연·월 후보가 없으면 1패스 후보를 지우지 않는다. 단, 패턴 등급이 같거나 높은 2패스 출력만 "다시 읽은 것"으로 인정 | +45/−4, 등급 인식으로 +8/−1 추가 |

### 5-2. 속도 및 오탐 최적화 전략

**속도**

| 전략 | 효과 |
| --- | --- |
| 탐지기·인식기 mobile 급 교체 | 5.8 → 1.8초 |

| JPEG 디코딩 단계 축소 | 24MP 원본 비용 절감 |

**오탐 억제**: 패턴 신뢰 등급(완전 날짜 > 공백·6자리 > 연월 > 월일), 9자리 이상 숫자열 마스킹, 연도 범위 2017~2031, 2자리 연도 상한 2028, 같은 등급 안에서만 가장 늦은 날짜, 파인튜닝 인식기는 폴백으로만(1순위로 두면 로트·시각 줄에서 날짜를 지어냄). 답한 것의 정밀도 86%.

## 7. 한계와 보완 계획

- **small 이미지 군집(33%, 75.8%)이 구조적 천장.** 640px 원본에 글자 8~12px. 업스케일·해상도 상향 모두 효과 없음. 촬영 가이드(날짜를 가운데, 가까이)로 입력 품질을 올리는 운영 대응이 현실적.
- **병기 71.1%.** 소비기한 줄 숫자 자체가 안 읽히는 경우가 남음. 한국어 인식기로 `소비·까지·EXP` 줄을 찾아 그 줄의 날짜를 후보에 보태는 2단계 안(`ITDA_KO_LINE`) 실측 det960 +40/−5 로 병기 71.1→75.2% 까지 닿지만 장당 +3.4s 라 보류. 병철 재탐지와 겹치는 영역이라 통합 때 함께 판정.
- **같은 글자의 이중 해석** (`24/10/2021 07/2020` 의 `2021 07/20`): 범위 가림 규칙이 대칭 결함 → 알려진 한계.
- **단독 `07-21` 영문 수입품**: 월.일로 읽음. 글자만으론 월/연과 구별 불가.
- **채점 서버 속도 미실측.** 시간 예산 가드로 완주는 보장하나, 서버가 Colab 2vCPU 급이면 경량 단계 발동으로 정확도 손실.
- **500장 완전 무오염 아님.** 예선 규칙 설계 시 500장 오답을 본 이력이 있어 각주로 명시.
