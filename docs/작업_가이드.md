## 공통 규칙

1. 시작 전 `git pull`. 하루에 두 번 이상.
2. **`main` 의 `predict.ipynb` 는 v3 고정.** 실험은 브랜치에서 (`git checkout -b yolo`), `compare.py` 비교표로 이긴 뒤에만 main 에 합침.
3. `requirements.txt` 를 바꾸면 반드시 3.10 Linux wheel 확인: `pip download --python-version 3.10 --only-binary=:all: --platform linux_x86_64 --platform manylinux2014_x86_64 <pkg>==<ver>`
4. 가중치(`.pt`, `.pth`)는 절대 커밋 금지 → `download_weights.sh` 에 다운로드 추가.
5. 보고는 카톡에 한 줄: `[줄기] 결과 숫자 / 막힌 것 / 다음`. 예: `[A] mAP50 0.91, 653장 비교 아직 / Colab 세션 끊김 / 내일 오전 비교`.

## 줄기 A — YOLO 날짜 영역 검출기 (보류 → 본선)

**9/10 저녁 판단**: PP-OCRv5 mobile 탐지기(300ms)가 속도 문제를 이미 풀었고 잡음은 패턴 등급으로 처리됨. 자동 박스 라벨(`labels/boxes/`)은 본선용으로 보존. 이 줄기의 인력은 **줄기 E(인식기 파인튜닝)** 로.

### (원안, 참고용)

**왜**: 검출기(CRAFT) 가 장당 시간의 절반 이상이고 EasyOCR 로는 못 줄임 (Colab 14s/장). YOLOv8n 은 0.1s. 잡음 날짜(품목보고번호·영양성분)도 같이 사라짐.

**받는 것** (9/11 오전, Claude 가 올림): `labels/boxes/` — YOLO 형식. `images.txt`(파일 목록), `labels/<image_id>.txt`(`0 cx cy w h` 정규화), `data.yaml`. v3 가 정답을 맞힌 이미지의 날짜 박스 ≈ 670개 (자동 생성) + 검토 필요 목록.

**할 것**
1. Colab GPU: `pip install ultralytics` → `yolo detect train model=yolov8n.pt data=data.yaml imgsz=640 epochs=50 batch=32` (30분 내외). **YOLOv8n** 으로 — 안내서 허용 목록에 있는 이름.
2. `best.pt` 를 드라이브 공개 링크 또는 GitHub Release Asset 으로. `download_weights.sh` 에 `curl -L <url> -o weights/yolo_date.pt` 추가.
3. 노트북 삽입 지점: 1패스의 `ocr_prioritized(small)` 앞. 함수 하나:
   ```python
   def detect_date_boxes(img):   # 원본 BGR → [(x0,y0,x1,y1), ...] 원본 좌표, 신뢰도 0.25 이상
   ```
   찾으면 → 각 박스를 여백 30% 로 크롭 → `reader.readtext(crop, allowlist=ALLOW_P1)` → 기존 `group_lines` → `parse_dates` → 기존 선택·가드 그대로.
   **못 찾으면 → 기존 v3 경로 그대로 (폴백).** 이게 있어서 v3 보다 나빠질 수 없다.
4. `requirements.txt` 에 `ultralytics==<3.10 wheel 있는 버전>` 추가 후 규칙 3 으로 확인. torch 2.2.2 와 호환되는 ultralytics 버전인지 확인 (8.1.x 권장).
5. 비교: `labels/README.md` 맨 아래 "정확도 측정" 순서대로 653장 실행 → `python notebooks/compare.py "v3=<v3 sub>|<v3 dbg>" "yolo=<sub>|<dbg>"`. v3 결과 파일은 Claude 가 `labels/eval_v3/` 에 올려 둠.

**관문**: 9/11 저녁 학습 결과 mAP50 보고. 9/12 저녁 비교표. 완전일치·필드평균·장당 시간 세 숫자 모두 v3 이상이면 교체.

## 줄기 B — 오답 원인 태깅 (담당: ___ , ___ )

**왜**: 통합 파이프라인이 틀린 132장의 원인을 지금은 텍스트 로그로 추정만 하고 있다. 사람이 사진을 보면 "정말 안 보임 / 보이는데 못 읽음 / 엉뚱한 걸 고름 / 라벨이 틀림" 이 갈리고, 그 비율이 남은 시간을 A 와 C 중 어디에 쓸지 결정한다. **코딩 없이 성능에 직접 기여하는 자리.**

**받는 것**: `notebooks/review.py` + `labels/review_int.csv` — 통합 파이프라인이 1차 500장에서 틀린 132장 (A/B 66장씩, 10분). 도구는 라벨링 창과 같은 모양 — 사진 위에 정답·예측이 표시되고 원인 코드 한 글자 치고 Enter.

**원인 코드**

| 코드 | 뜻 | 예 |
| --- | --- | --- |
| `u` | 사람 눈에도 안 보임 (저화질·흐림·가림) | 640px 에서 글자가 뭉개짐 |
| `r` | 보이는데 OCR 이 잘못 읽음 | `2026.03.20` 을 `2026-03-02` 로 |
| `s` | 날짜는 읽혔는데 엉뚱한 숫자를 골랐음 | 품목보고번호·로트 |
| `p` | 제조·소비 병기에서 잘못 고름 | 제조일자를 냄 |
| `f` | 형식을 파서가 모름 | 처음 보는 표기 |
| `l` | **라벨이 틀림** (정답이 잘못 적힘) | 그 자리에서 정답 수정 |
| `o` | 기타 — 메모에 한 줄 |

150장씩 나눠서 장당 10초, 25분. 끝나면 `labels/review_v3.csv` 커밋. `l` 은 라벨 파일도 같이 고침 (`labels_block<N>.csv` 의 raw).
