## 1. 개괄

### 1-1. 핵심 접근 방식 요약

식품 포장 사진에서 소비기한을 읽는 문제를 **경량 사전학습 OCR + 날짜 해석 규칙 + 못 읽은 사진 전용 재시도**로 풀었다. 채점 조건(4코어 CPU, GPU 없음, 500장 2,500초, 인터넷 차단)이 설계를 정했다. 설계 원칙은 하나다. **틀릴 때 안전하게 틀리도록 만든다.** 확신이 없으면 날짜를 지어내지 않고 '미인식'으로 답한다.

이 보고서는 풀어야 했던 문제를 먼저 적고, 문제마다 대응과 측정값을 붙였다.

| 누구의 문제 | 문제 | 대응 | 측정값 | 절 |
| --- | --- | --- | --- | --- |
| 구매자 | 적힌 날짜가 맞는지 확인할 방법이 없다 | 판독 날짜·남은 일수·날짜면 원본을 게시글에 표시 | 남은 날을 많게 읽는 오류 4.9% 를 따로 측정 | 4-3, 6-2 |
| 판매자 | 포장에서 날짜를 찾아 손으로 옮겨 적는다 | 날짜면을 찍으면 확신할 때만 칸을 채우고, 판매자가 확인한다 | 폰 사진 389장: 41 ~ 45% 자동 입력, 틀린 값을 받는 판매자 8 ~ 10% | 6-2 |
| 플랫폼 | 위반을 게시 뒤에 찾는다 | 게시 전 안내, 기한이 지난 글 자동 숨김 | 건강기능식품 게시글의 3.05% 가 위반 조치 `[보도]` | 6-1 |
| 모델 | 포장에 날짜가 아닌 숫자가 많다 | 긴 숫자열 제거, 신뢰 등급 | 시험 문자열 26종 | 3-3 |
| 모델 | 제조일과 소비기한이 함께 찍힌다 | 늦은 날짜 선택, 주변 재탐지, 구분자 일치 | 64.9 → 78.3% | 3-3 |
| 모델 | 도트 인쇄·각인·저해상도 | 못 읽은 사진에만 재시도, 그래도 없으면 미인식 | +17/−0 | 3-2 |

| 모델 | 서버 속도를 모른다 | 시간 예산 가드 | 한도의 55 ~ 79% | 5 |

제공 데이터의 특징: 긴 변 700px 이하인 저해상도 사진이 33%, 제조일·소비기한 병기가 10%, 도트 인쇄와 각인이 많다. 이 세 무리가 오답의 대부분이다.

### 2-2. 라벨링 규칙 정의 및 수행 절차

**규칙을 먼저 문서로 정하고, 라벨링 도구와 모델이 같은 규칙을 쓰게 했다.** 모호한 표기는 팀의 후처리 규칙으로 채점한다는 운영진 확정에 맞춘 설계다.

| 구분 | 내용 |
| --- | --- |
| 사람이 하는 일 | 포장에 찍힌 **그대로** 입력(`2027.06.26`, `FEB/26/21`, `30 12 23`). 형식을 바꾸지 않는다 |
| 도구가 하는 일 (자동 규칙) | 연도가 뒤면 일/월/년, 2자리 세 개는 년/월/일 우선, 공백 구분은 일/월/년, 영문 월 처리, 연·월만 있으면 `YYYY-MM-NONE`, 월·일만 있으면 `NONE-MM-DD` |
| 사람이 판단하는 범위 | 두 날짜 병기는 늦은 날짜, 제조·포장일자만 있으면 `NONE`, 판독 불가, 애매함 등 태그 9종 |
| 수행 | 5명이 블록 단위로 분담, 해상도별로 섞어 무작위 배정. 파이프라인은 실행할 때마다 도구와 규칙이 같은지 자가검증 |

**정답 라벨도 검증했다.** 최종 구성 직전의 오답 446장을 사람이 전부 다시 봤다. 라벨 오류가 16장(오답의 3.6%)이었고, 그중 **11장은 모델이 맞고 사람이 틀린 것**이었다. 고친 값은 누가·언제·무엇을 바꿨는지 기록했다. 점검자가 고친 18장 중 3장은 규칙 문서와 어긋나 다시 바로잡았다. 사람이 입력한 날짜도 틀린다는 이 경험이 6절 설계(판매자 입력을 사진과 나란히 보여 주고, 고친 값은 검증한 뒤에만 학습에 쓴다)의 출발점이다.

## 3. 아키텍처 설계 논리

### 3-1. 전체 파이프라인 아키텍처 구조도

(그림 자리: `docs/img/architecture.png` — 최종 구성으로 다시 그릴 것)

```
사진
 ├─ ① 1차 읽기 (640px)   글자 위치 탐지 → 큰 글자부터 인식. 완전한 날짜를 찾으면 잔글씨 생략
 │      └ 후보 없음 → 1,024px 재시도 → 도트 인쇄 전처리 후 재시도
 ├─ ② 다시 읽기           날짜 후보 줄만 원본 해상도로 재인식 → 1차 결과와 다수결
 │      ├ [본선] 다시 읽은 결과가 1차 후보를 지우지 못하게 함
 │      ├ [본선] 일(日)이 한 자리로 읽히면 글자 상자를 넓혀 재인식
 │      └ [본선] 깨져 읽힌 날짜 모양 줄을 다시 읽어 둘 이상 일치할 때만 후보에 추가
 ├─ ③ [본선] 주변 재탐지   후보 줄 옆에 크기 비슷한 숫자 줄이 있을 때만 원본 해상도로 다시 탐지
 ├─ ④ 못 읽은 사진 전용    파인튜닝 인식기로 재시도 → [본선] 작은 사진은 2배 확대해 재시도
 ├─ ⑤ 해석·선택           형식 정규화 → 신뢰 등급 → 연도 범위 → 같은 등급 안에서 가장 늦은 날짜
 ├─ 시간 예산 가드         예상 소요가 예산을 넘으면 단계를 줄임. 결과 파일은 반드시 생성
 └─ 출력  YYYY-MM-DD / YYYY-MM-NONE / NONE-MM-DD / NONE
```

딥러닝 모델은 탐지기 1개와 인식기 2개(사전학습, 우리 라벨로 파인튜닝)이고 합쳐 약 21MB 다. 나머지는 전부 규칙이다. 비용이 큰 단계는 모두 조건부라, 대부분의 사진은 ①·②·⑤ 만 거친다.

### 3-3. 후처리 규칙 설계

**(1) 소비기한과 다른 숫자의 구분**

| 헷갈리는 숫자 | 구분 방법 | 확인 |
| --- | --- | --- |
| 품목보고번호·바코드·제조번호 | 9자리 이상 숫자열 제거 | 시험 문자열 6종 모두 날짜로 읽히지 않음 |
| 전화번호 | 날짜 형식(자릿수·구분자·연도 범위)에 맞지 않아 걸러짐 | 시험한 10종 중 9종은 날짜로 읽히지 않음. 가운데가 연도처럼 보이는 휴대전화 번호 1종만 낮은 등급 후보가 됐고, 완전한 날짜가 있으면 등급 규칙이 무시 |
| 영양성분 숫자, 시각, 생산 라인 기호 | 신뢰 등급: 완전한 날짜가 있으면 공백 구분·6자리 압축 같은 약한 패턴은 보지 않음 | 등급 도입으로 500장 +15장. 시각·용량 8종 모두 날짜로 읽히지 않음 |

| 제조일자 | 같은 등급 안에서 가장 늦은 날짜 (소비기한 ≥ 제조일) | 병기 78.3% |
| 두 날짜에 걸친 가짜 날짜 (`2025.09.09 2026.09.08` 의 `09.09 2026`) | [본선] 구분자가 섞인 쪽을 버림 | +10/−0 |

**(2) 날짜 정규화**

| 표기 | 해석 |
| --- | --- |
| 4자리 연도가 앞 / 뒤 | 연월일 / 일월연 |
| 2자리 세 개 (`26.03.20`) | 년/월/일 우선. 불가능하거나 연도가 2028 이상이면 일/월/년 |
| 같은 사진에 `BBD` `EXP` `BEST BEFORE` 가 있음, 또는 공백 구분 | 일/월/년 |
| 미국식 | 일/월/년이 불가능할 때만 월/일/년 |
| 영문 월 (`FEB/26/21`, `22OCT2021`) | 월 위치를 확정하고 나머지를 자릿수로 판단 |
| 연·월만 / 월·일만 | `YYYY-MM-NONE` / `NONE-MM-DD` |
| 잘못 읽힌 글자 | `2O27` → `2027`, 도트 조각 사이 공백 제거, 구분자 하나 빠짐 허용 |
| [본선] 콜론 구분, 날짜 뒤에 붙은 숫자(`21.02.10011`), 연·월 사이 구분자 빠짐(`202104.19`) | 각각 +6/−0, +16/−1, +8/−1 |

**(3) 미인식 `NONE` 기준**: 후보가 0개면 `NONE`. 자주 나오는 날짜를 찍지 않는다. 연도나 일만 없으면 그 칸만 `NONE` 으로 둔다. 시간 예산 가드의 마지막 단계에서 남은 사진도 `NONE` 으로 채워 결과 파일을 만든다.

| 규모 | 건강기능식품 개인 간 거래 게시글 482,675건, 그중 규정 위반 조치 14,729건(3.05%). 위반 유형은 개봉 2,632 · **소비기한 미준수 725** · 의약품 오인 654 · 해외직구 465 (2024-05 ~ 2025-12, 식약처 자료) `[보도]` |
| 시의성 | 추석 직후 선물세트 거래량이 작년 연휴 대비 50% 증가 `[보도]`. 선물세트는 날짜가 인쇄된 미개봉 가공식품·건강기능식품이라 대회 데이터와 같은 종류다 |
| 지금의 처리 | 게시 뒤에 머신러닝·키워드 모니터링·이용자 신고로 찾아 삭제한다. 플랫폼이 사진을 OCR 로 읽는다는 보도는 건강기능식품 인증마크가 **있는지** 확인하는 용도였다 `[보도]` |
| 빈칸 | 같은 사진에서 소비기한 **값**을 읽는다는 자료는 찾지 못했다. 가공식품 게시글에 소비기한 칸은 있으나(팀 확인) 입력값이 맞는지는 아무도 모른다 |
| 선례 | 일본 메루카리는 식품을 올릴 때 소비기한 인쇄 부분의 사진을 필수로 요구한다. 자동으로 읽는다는 자료는 찾지 못했다 |
| 1차 대상 | 위반 통계가 공개된 건강기능식품 카테고리. 거래 조건은 미개봉, **소비기한 이내**, 연 10회 이하다. 2025년 5월에 '잔여 6개월 이상' 조건이 '소비기한 이내'로 바뀌어, 날짜로 판정할 것은 기한이 지났는지 하나다 |
| 하지 않는 것 | 사기 방지, 개봉 여부 판별. 날짜에 스티커를 붙이거나 다른 상품을 찍으면 막지 못한다 |

**목적을 좁혔다.** 이 시스템은 속이려는 소수를 잡는 장치가 아니다. 규칙을 모르거나 날짜를 확인하지 않고 올리는 다수를 게시 전에 돕는다. 속이려는 소수는 기존 사후 모니터링이 맡는다.

**모델이 틀리면 어디로 가는가.** 판매자가 마지막에 확인하므로, 모델의 실수는 대부분 판매자의 수정 한 번으로 끝난다.

| 모델 결과 | 판매자에게 일어나는 일 | 남는 위험 |
| --- | --- | --- |
| 맞게 읽음 | 채워진 날짜를 확인 | 없음 |
| 미인식, 또는 확신이 낮음 | 빈칸. 손으로 입력 | 지금과 같음 |
| 이르게 읽음 | 날짜 확대본을 보고 고침 | 안 고치면 남은 날이 적게 표시 (판매자에게 불리) |
| 늦게 읽음 | 날짜 확대본을 보고 고침 | **안 고치면 남은 날이 많게 표시** → 아래 대응 |

판매자가 확인한다는 조건에서 정확도는 안전성이 아니라 **자동 입력 비율**을 정한다. 모델을 사람의 판독 정확도와 비교하지 않는다.

### 6-2. 운영 아키텍처 설계 (서버 / 온디바이스)

**구성**: 플랫폼 서버에서 추론한다. 모델 21MB, CPU 전용, GPU 와 외부 API 가 필요 없다. 폰 안에서 도는 방식은 해 보지 않았으므로 다음 단계로 둔다.

```
판매자: 카테고리 선택 → 날짜면 촬영 (해상도·흐림 검사, 미달이면 바로 재촬영)
   → 서버 판독 (판매자가 제목·가격을 쓰는 동안)
   → 확신도가 기준 이상이고 완전한 날짜면 소비기한 칸 자동 입력, 아니면 빈칸
   → 판매자가 날짜 확대본을 보며 확인 또는 수정
   → 게시글에 "판매자 사진에서 읽은 날짜 · 남은 일수 · 날짜면 원본" 표시
   → 기한 임박 시 판매자에게 알림, 기한이 지나면 게시글 자동 숨김
기록: 원본 사진, 촬영 시각, 판독값, 확신도, 판매자 수정 이력, 모델 버전
```

**처리 시간** `[재집계]` — 폰 사진 389장은 절반이 3.8초 안에 끝났지만 32% 는 10초를 넘겼다(가장 긴 것 84초). 10초를 넘긴 123장 중 맞힌 것은 13장뿐이고 88장은 끝내 미인식이었다. 그래서 **10초 안에 답이 없으면 빈칸**으로 둔다. 이렇게 해도 자동 입력은 44.7 → 40.6% 로 조금 줄고, 틀린 값을 받는 판매자는 10.3 → 8.2% 로 준다(확신도 0.7 기준). 대회용 시간 예산 가드와 같은 생각이다.

**자동 입력 기준** `[재집계]` — 완전한 날짜로 읽힌 것만 채운다. 비율의 분모는 전체 사진이다.

| 자동 입력 기준 | 자료 | 채워지는 비율 | 채운 값의 정확도 | 틀린 값을 받는 판매자 | 그중 늦게 읽은 값 |
| --- | --- | --- | --- | --- | --- |
| 기준 없음 | 폰 사진 389장 | 70.2% | 70.3% | 20.8% | 4.6% |
| **확신도 0.7 이상** | 폰 사진 389장 | **44.7%** | **77.0%** | **10.3%** | 3.3% |
| 확신도 0.9 이상 | 폰 사진 389장 | 16.5% | 87.5% | 2.1% | 0.8% |
| 확신도 0.7 이상 | 봉인 500장 | 62.0% | 92.9% | 4.4% | 1.6% |

- 기준은 플랫폼이 고른다. 기준을 올리면 틀린 값은 줄고 손으로 입력하는 판매자가 는다.
- **기준을 0.7 로 둔 근거**: 기준 없음 → 0.7 은 틀린 값 41장을 피하려 맞는 값 58장을 포기하고(1.4 대 1), 0.7 → 0.9 는 32장을 피하려 78장을 포기한다(2.4 대 1). 틀린 값 하나의 비용이 맞는 값 하나의 이득의 1.4 ~ 2.4배일 때 0.7 이 맞다.
- **확신도만으로는 위험한 쪽의 오류가 잘 걸러지지 않는다.** 폰 사진에서 늦게 읽은 18장 중 13장이 확신도 0.7 이상이었다. 그래서 확신도 기준에 아래 세 장치를 더한다.

| 장치 | 내용 | 막는 것 |
| --- | --- | --- |
| 날짜 확대본 | 채운 값 옆에 사진의 날짜 부분을 확대해 보여 준다 | 판매자가 보지 않고 확인을 누르는 것 |
| 최대 기한 검사 (보조) | 읽은 날짜가 제품 유형별 최대 소비기한을 넘으면 빈칸으로 둔다. 설계 단계이고 효과는 재지 못했다 | 크게 늦게 읽은 값만 |
| 확신이 낮은 값은 숨기고 대조 | 기준 미만의 판독값은 보여 주지 않고 판매자가 먼저 입력하게 한 뒤, 판독값과 다르면 확대본을 보여 준다 | 채워 준 값을 같은 사람이 확인하는 것만으로는 검증이 아니라는 문제 |

**판정은 안내까지만 한다.**

| 상황 | 판매자에게 | 게시글 표시·기록 |
| --- | --- | --- |
| 확인한 날짜가 거래 조건을 충족 | 없음 | 판독 날짜, 남은 일수, 날짜면 원본 |
| 확인한 날짜가 기한 경과 | 사유 안내. 날짜가 잘못 읽혔으면 고치거나 다시 찍을 수 있음 | 게시 보류. 이의 제기 때만 사람이 검토 |
| 채워진 값을 판매자가 다른 날짜로 고침 | 날짜 확대본을 다시 보여 주고 한 번 더 확인 | 판독값과 입력값을 둘 다 기록. 사후 검토의 우선순위 신호로만 사용 |
| 미인식, 다시 찍어도 미인식 | 손으로 입력 | "사진에서 날짜를 읽지 못함" 표시 |

수정만으로 제재하지 않는다. 폰 사진에서는 채운 값의 23% 가 틀린 값이라, 수정의 대부분은 모델의 오독을 바로잡은 것이다.

**판독값만으로 자동 차단하지 않는다.** 모델이 읽은 날짜만 보고 판정하면 얼마나 틀리는지 계산했다.

| `[가정]` 실제 날짜가 고르게 분포, 판독값만으로 판정 | 봉인 500장 | 폰 사진 389장 |
| --- | --- | --- |
| 기한이 남은 글(1~365일)이 지난 것으로 읽힘 | 3.2% | **11.2%** |
| 기한이 지난 글(1~180일 경과)이 남은 것으로 읽힘 | 1.9% | 2.4% |
| 기한이 지난 글이 지난 것으로 읽힘 | 92.8% | 70.5% |

폰 사진에서는 정상 게시글 아홉에 하나를 막게 된다. 그래서 판정은 판매자가 확인한 날짜로 하고, 모델은 칸을 채우는 데까지만 쓴다.

플랫폼이 '확인됨'을 보증하지 않고 **판독값과 원본을 보여 주는 것**도 같은 이유다. 보증 표시는 조작된 날짜에 신뢰를 빌려준다. 원본과 수정 이력은 신고가 들어왔을 때 근거가 된다.

**선물세트**: 여러 상품이 든 세트에서 구매자에게 중요한 것은 가장 이른 소비기한이다. 우리 규칙은 한 사진에서 가장 늦은 날짜를 고른다(제조일과 구분하기 위해). 그래서 상품별로 따로 찍게 하고, 세트의 표시값은 그중 가장 이른 날짜로 한다.

**쓸수록 나아지는 구조**: 판매자가 고친 값은 그 사진의 라벨이 된다. 다만 사람이 입력한 값도 틀린다(2-2절: 점검자가 고친 18장 중 3장이 규칙과 어긋남). 고친 값은 표본 검수를 거친 뒤에만 학습에 쓴다. 수정값에는 글자 위치가 없어 학습용 글자 조각은 따로 확보해야 한다.

### 6-3. 예상 운영 비용 산출

1차 대상(건강기능식품 카테고리) 기준. 게시글 수는 482,675건 ÷ 20개월 ≈ 월 2.4만 건, 하루 약 800건 `[보도]`.

| 항목 | 계산 | 값 |
| --- | --- | --- |
| 하루 연산 시간 | 800장 × 장당 4.0초 (느린 쪽 PC 값) | 약 53분. 4코어 서버 1대의 4% |
| 어려운 사진이 많을 때 | 800장 × 장당 10.8초 (폰 사진 389장 평균. 10초 제한을 걸면 5.2초) | 약 2.4시간. 서버 1대의 10% |
| 서버 비용 — 전용 1대 | 국내 클라우드 4 vCPU·8GB, 시간당 196원 (부가세 별도) `[보도]` | 월 약 14만 원, 연 약 169만 원 |
| 서버 비용 — 기존 서버의 여유분 사용 | 위 금액 × 사용률 4 ~ 10% | 연 약 7만 ~ 17만 원 |
| **게시글 한 건당** | 연 7만 ~ 169만 원 ÷ 연 약 29만 건 | **0.2 ~ 5.8원** |
| 라이선스·GPU·학습비 | 공개 모델, 무료 학습 | 0원 |
| 사람 검토 | 이의 제기 건만 | 발생률 미측정 `[가정]` |
| 사진 저장 | 장당 3MB `[가정]` × 월 2.4만 장 | 월 약 72GB |

연산 비용은 작다. 다만 개발·앱 화면 변경·운영 인력, 판매자가 사진을 한 장 더 찍는 부담은 포함하지 않았다.

### 6-4. 비즈니스 손실 절감 효과 및 ROI 기획

**비용은 게시글 한 건에 0.2 ~ 5.8원이다.** 편익이 이보다 크면 이익이다.

**편익을 OCR 이 있어야 되는 것과 아닌 것으로 나눴다.** 남은 일수 표시와 기한이 지난 글 자동 숨김은 날짜 칸만 있으면 된다. OCR 이 보태는 것은 그 칸의 값이 사진과 맞는지다.

| 가치 | 누구에게 | OCR 이 있어야 하나 | 근거 |
| --- | --- | --- | --- |
| 입력값과 사진의 대조 | 구매자, 플랫폼 | 예 | 손으로 옮겨 적은 날짜는 틀린다. 우리 라벨에서 찾은 오류 16장 중 8장이 숫자 한 글자였다. 판매자가 손으로 넣거나 고친 값이 틀렸을 때 그 값이 판독값과 우연히 같아 지나갈 확률은 봉인 500장 평균 0.2%, 폰 사진 0.4%. 틀리게 채워진 값을 판매자가 그대로 둔 경우는 이 대조로 잡지 못하고 날짜 확대본과 최대 기한 검사가 맡는다 |
| 날짜면이 찍혔는지 확인 | 구매자 | 예 | 날짜가 읽히지 않으면 게시글에 표시. 메루카리는 이 확인을 사람이 한다 |
| 입력 편의 | 판매자 | 예 | 폰 사진 기준 41 ~ 45% 자동 입력 (10초 제한을 걸면 41%) |
| 라벨 축적 | 플랫폼 | 예 | 판매자 수정값으로 자동 입력 비율이 오른다 |
| 남은 일수 표시, 기한이 지난 글 자동 숨김 | 구매자, 플랫폼 | 아니오 | 날짜 칸만으로 가능. OCR 의 편익으로 세지 않았다 |

**인력 절감으로는 가치를 설명하지 않는다.** 금액으로 말할 수 있는 편익은 위반 게시글의 사후 처리비뿐인데, 손익분기로 계산하면 본전이 되지 않는다.

| 조건 | 연간 소비기한 위반 | 걸러지는 비율 `[가정]` | 연간 비용 | 손익분기 1건당 처리비 |
| --- | --- | --- | --- | --- |
| 20개월 평균 (옛 6개월 조건 포함), 기존 서버의 여유분 | 435건 (725 ÷ 20 × 12) | 50% | 17만 원 | 약 780원 |
| 조건 완화 뒤 추정, 기존 서버의 여유분 | 약 180건 | 50% | 17만 원 | 약 1,900원 |
| 조건 완화 뒤 추정, 전용 서버 | 약 180건 | 50% | 169만 원 | 약 1만 9천 원 |

- 위반 1건을 사람이 30초에 검토하면 최저시급 기준 약 86원이다 `[가정]`. 손익분기 처리비는 기존 서버의 여유분을 쓸 때도 이보다 9 ~ 22배 크다. 개발과 앱 화면 변경 비용, 판매자가 사진을 한 장 더 찍는 부담도 여기에 들어 있지 않다.
- 조건 완화 뒤 추정: 첫 1년 608건, 20개월 누적 725건이므로 그 뒤 약 8개월에 117건이다 `[보도]`.
- 그래서 이 기획의 가치는 단속이 아니라 **날짜를 확인할 수 있는 정보로 만드는 것**에 있고, 그 값을 게시글 한 건당 0.2 ~ 5.8원에 얻는다.

**플랫폼이 도입할 이유는 비용 절감이 아니라 규제 대응이다.** 건강기능식품 개인 간 거래는 시범사업이고, 국회에서 모니터링 인력이 5명이라는 지적을 받았으며 거래를 금지하는 법안이 계류 중이다 `[보도]`. 게시글마다 날짜면 사진과 판독 기록이 남는 것은 관리 체계의 증거가 된다. 이 가치는 금액으로 재지 못했다.

**다른 현장과의 연결**: 뼈대는 '읽은 값을 기준값과 대조하고 예외만 사람에게 넘긴다'이다. 출하 표시물 검증에서는 기준값이 품목 마스터, 여기서는 판매자 입력이다. 기록 항목(원본·판독값·수정 이력·모델 버전)은 감사 추적이고, 4-2 의 채택 기준과 봉인 500장은 모델을 바꿀 때의 재검증 기준이다.

**단계별 확장**: 1단계 건강기능식품 카테고리, 서버 추론 → 2단계 가공식품·명절 선물세트, 폰 자체 추론 → 3단계 지금은 잡음으로 지우는 품목보고번호를 읽어 제품 조회와 회수 대상 확인. 같은 파이프라인은 식품공장의 출하 전 날짜 인쇄 확인에도 쓸 수 있다. 공장은 정답(제조일 + 품목별 소비기한 일수)을 알기 때문에 읽은 값을 대조만 하면 되고, 기대값을 일부러 어긋나게 넣은 실험에서 오인쇄를 놓칠 확률은 한 장당 평균 0.2% 였다.
