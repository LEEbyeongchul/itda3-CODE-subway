## 4. 남은 오류의 성격 (v3 기준, 653장 중 304장 오답)

- 미인식 ~154장: 대부분 small 층. 인식기가 글자를 못 읽음 (`'4684 23. 0 ../ 615'`). 규칙으로 회수 불가
- 월/일 자리 오독 (연도 맞음): 도트 프린터 `0↔8`, `1↔7`, 자리 탈락. 인식기 품질 문제
- 병기에서 선택 오류: 제조·소비 둘 다 읽혔는데 잘못 고름 — 키워드(`소비기한`/`까지`) 신호가 없어서. 한글 인식기 추가는 비용 대비 검토 필요
- 조각 복원의 부작용: 가짜 후보가 "더 늦은 날짜"로 이김 (12장). 확인 신호로는 못 가림 (§3)

## 4.5 속도 — 채점 서버 흉내 (개발 PC 스레드 제한, 층화 100장)

| 스레드 | 장당 평균 | p90 | 500장 환산 | 판정 |
| --- | --- | --- | --- | --- |
| 8 (개발 PC 기본) | 4.12s (653장) | 7.7s | 2062s | 여유 적음 |
| 4 | 3.37s | 6.2s | 1683s | 안전 |
| 2 | 4.88s | 8.8s | **2438s** | **초과** |

채점 서버 "4 vCPU" 가 물리 2코어+HT 면 2스레드 쪽에 가까움 → 턱걸이 초과 위험. 대응: **시간 예산 가드**(`TIME_BUDGET_S=2000`). 20장 이후 예상 총 소요가 예산을 넘으면 남은 장을 경량 모드로 처리해 완주를 보장한다. 경량 모드에서의 정확도 손실은 사다리(1024 재시도 4.3% 장, 정밀도 50%)와 영문 폴백(3.7%)에 국한.
**가드 발동 검증** (2스레드, 예산을 300s 로 낮춰 강제 발동, 층화 100장): 20장 시점 예상 359s > 300s → 경량 모드 전환 확인. 이후 80장에서 1024 재시도·영문 폴백 0회. 장당 4.96s → 3.66s. 정확도 24/50 → 21/50 (라벨된 50장) — 손실은 사다리·폴백 의존 케이스에 국한. 완주 보장의 대가로 감수.
**Colab CPU 실측 (병철, 2 vCPU Xeon 2.2GHz, Python 3.13, 랜덤 100장): 장당 14.22s, 100장 1422s → 500장 환산 7110s.** 개발 PC 의 3.5배. 채점 서버(4 vCPU)가 Colab 의 2배라 해도 장당 7s = 3500s 로 초과.
→ 가드를 **3단계**로 강화: 1단계(사다리 640만·폴백 생략) → 2단계(640·박스 10·2패스 생략) → 3단계(남은 장 NONE, CSV 는 반드시 생성). 최근 20장 속도로 예측해 단계를 올린다.
- 단계 상승 사슬 검증(예산 100s 강제, 100장): 20장→1단계, 40장→2단계, 60장→3단계, CSV 100행 생성 ✓
- **2단계를 480px 로 설계했던 안은 폐기**: 653장 완전일치 53.4% → **6.4%** (small 0%, mid 0%, large 17%). 640 원본을 480 으로 줄이면 글자가 ~5px 라 인식기가 못 읽음. 해상도는 못 줄인다.
- 정직한 결론: 장당 시간의 절반 이상이 검출기(CRAFT VGG16)이고 이건 EasyOCR 로는 못 줄인다. Colab 급 서버(14s/장)에선 3단계가 불가피 → 처리된 장만 점수. 채점 서버가 AWS c5.xlarge 급(3.4GHz 4vCPU)이면 Colab 의 3~4배라 정상 모드로 완주 가능. **가벼운 전용 검출기(YOLOv8n 급, 50~100ms)가 속도 문제의 근본 해법** — 팀 기술 계획 Phase 2 의 가장 강한 근거.
