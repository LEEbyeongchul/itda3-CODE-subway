## 1. 개괄

### 1-1. 핵심 접근 방식 요약

식품 포장 사진에서 소비기한을 읽는 문제를 **경량 사전학습 OCR + 날짜 해석 규칙 + 못 읽은 사진 전용 재시도**로 풀었다. 채점 조건(4코어 CPU, GPU 없음, 500장 2,500초, 인터넷 차단)이 설계를 정했다. 원칙은 하나다. **틀릴 때 안전하게 틀린다.** 확신이 없으면 날짜를 지어내지 않고 '미인식'으로 답한다. 풀어야 했던 문제와 대응, 측정값은 아래와 같다.

| 문제 | 대응 | 측정값 | 절 |
| --- | --- | --- | --- |
| 구매자는 적힌 날짜를 확인할 수 없다 | 판독 날짜와 날짜면 원본을 게시글에 표시 | 남은 날을 많게 읽는 오류 4.9% 를 따로 측정 | 6 |
| 판매자는 날짜를 손으로 옮겨 적는다 | 확신할 때만 칸을 채우고 판매자가 확인 | 폰 사진의 41 ~ 45% 자동 입력 | 6 |
| 포장에 날짜가 아닌 숫자가 많다 | 긴 숫자열 제거, 신뢰 등급 | 시험 문자열 26종 | 3-3 |
| 제조일과 소비기한이 함께 찍힌다 | 늦은 날짜 선택, 주변 재탐지 | 64.9 → 78.3% | 3-3 |
| 도트 인쇄·각인·저해상도 | 못 읽은 사진에만 재시도 | +17/−0 | 3-2 |
| 개발 데이터와 실제 폰 사진이 다르다 | 직접 찍은 389장으로 따로 측정 | 86.2% 대 52.4% | 4-2 |
| 채점 서버 속도를 모른다 | 시간 예산 가드 | 한도의 55 ~ 79% | 5 |
| 정답 라벨도 틀린다 | 오답 전수 재점검 | 오류 16장 중 11장은 모델이 맞음 | 2-2 |

제공 데이터는 저해상도(긴 변 700px 이하) 33%, 제조일·소비기한 병기 10% 이고 도트 인쇄와 각인이 많다. 이 세 무리가 오답의 대부분이다.

### 2-2. 라벨링 규칙 정의 및 수행 절차

**규칙을 먼저 문서로 정하고, 라벨링 도구와 모델이 같은 규칙을 쓰게 했다.**

| 구분 | 내용 |
| --- | --- |
| 사람 (수동) | 포장에 찍힌 그대로 입력(`FEB/26/21`, `30 12 23`). 병기는 늦은 날짜, 제조일자만 있으면 `NONE`, 판독 불가 등 태그 9종 |
| 도구 (자동 규칙) | 연도가 뒤면 일/월/년, 2자리 세 개는 년/월/일 우선, 공백 구분은 일/월/년, 영문 월, 연·월만 있으면 `YYYY-MM-NONE` |
| 수행 | 5명이 블록 단위로 분담, 해상도별로 섞어 무작위 배정. 파이프라인은 실행 때마다 도구와 규칙이 같은지 자가검증 |

**정답 라벨도 검증했다.** 오답 446장을 사람이 전부 다시 봤다. 라벨 오류가 16장이었고 그중 11장은 모델이 맞고 사람이 틀린 것이었다. 8장은 숫자 한 글자를 잘못 옮긴 것이다. 점검자가 고친 18장 중 3장도 규칙과 어긋나 다시 바로잡았다. 사람이 옮겨 적은 날짜는 틀린다는 이 경험이 6절의 출발점이다.

### 2-3. 전처리 내용

긴 변 640px 로 줄여 읽고 후보가 없을 때만 1,024px 로 다시 읽는다(해상도를 올려도 ±1%p 에 시간만 30~50% 늘고, 480px 로 내리면 53.4 → 6.4% 로 무너진다. 초기 구성 실험). 허용 문자 밖의 글자는 지우지 않고 공백으로 바꾼다(지우면 `2021(3)` 이 `20213` 으로 붙는다). 후보가 없는 사진에만 도트 인쇄용 침식·블러를 건다(500장 +17/−0). 9자리 이상 이어진 숫자는 해석 전에 지운다(품목보고번호 앞 8자리가 날짜로 읽힌다).

## 3. 아키텍처 설계 논리

### 3-1. 전체 파이프라인 아키텍처 구조도

(그림 자리: `docs/img/architecture.png`)

```
사진
 ├─ ① 1차 읽기 (640px)  글자 위치 탐지 → 큰 글자부터 인식. 완전한 날짜를 찾으면 잔글씨 생략
 │      └ 후보 없음 → 1,024px 재시도 → 도트 인쇄 전처리 후 재시도
 ├─ ② 다시 읽기          후보 줄만 원본 해상도로 재인식 → 1차 결과와 다수결
 │      └ [본선] 1차 후보를 지우지 못하게 함 · 글자 상자 넓히기 · 깨진 줄 다시 읽기
 ├─ ③ [본선] 주변 재탐지  후보 줄 옆에 크기 비슷한 숫자 줄이 있을 때만
 ├─ ④ 못 읽은 사진 전용   파인튜닝 인식기 → [본선] 작은 사진은 2배 확대
 ├─ ⑤ 해석·선택          형식 정규화 → 신뢰 등급 → 연도 범위 → 가장 늦은 날짜
 ├─ 시간 예산 가드        예상 소요가 예산을 넘으면 단계를 줄임
 └─ 출력  YYYY-MM-DD / YYYY-MM-NONE / NONE-MM-DD / NONE
```

모델은 탐지기 1개와 인식기 2개, 합쳐 약 21MB 다. 나머지는 규칙이다. 비용이 큰 재시도는 모두 조건부라 사진의 88% 는 재시도 없이 끝난다.

## 4. 모델 선택 근거 및 성능 평가

### 4-1. 비교한 모델·대안과 최종 선택 근거

| 비교 대상 | 결과 | 판단 |
| --- | --- | --- |
| EasyOCR 탐지 + 인식 | 39.1%, 장당 약 5초 | 속도 초과 |
| **PP-OCRv5 mobile 탐지 + 인식** | 67.7%, **1.8초** | **채택** (인식기 v3·v4·v5 중 v5) |

위 표 첫 세 줄의 정확도는 초기 라벨 133장 기준이다.

### 4-2. 날짜 추출 정확도 결과

**검증 방법**: 정답은 팀이 직접 라벨링한 3,352장이고 연·월·일이 모두 같아야 정답이다. 500장은 봉인하고 채택 판정은 나머지 2,852장에서만 했다. 새로 맞힌 장과 새로 틀린 장을 따로 세어 **퇴보가 회복의 1/3 을 넘으면 기각**했다. 임계값을 데이터에 맞추지 않고 구조 규칙만 채택했다.

| 측정 | 완전일치 | 필드평균 | 그 외 |
| --- | --- | --- | --- |
| 봉인 500장 | **86.2%** | **90.8%** | 미인식 3.0%, 답한 것의 정밀도 88.9% |
| ├ 해상도별 | 저 83.7 · 중 89.5 · 고 86.7% | | 병기 51장 78.4% |
| 판정용 2,852장 | **86.7%** | | 병기 78.3% · 비병기 87.7% |
| 직접 찍은 폰 사진 389장 | **52.4%** | 62.8% | 오답 중 미인식 21.9% (모델이 답하지 않은 사진은 88장, 22.6%), 답한 것의 정밀도 66.8% |
| ├ 찍은 사람별 | 44.0 · 44.1 · 52.0 · 69.8% | | 각인 표시 11장 18.2% |

튜닝에 쓴 사진(86.7%)과 쓰지 않은 사진(86.2%)의 수치가 비슷하다. 폰 사진 389장은 어려운 유형을 골라 찍은 것이라 실제 판매자 사진의 평균은 아니다. 다만 6절의 서비스가 받는 입력과 가장 가까워, **6절의 운영 수치는 이 389장으로 계산했다.**

단계별 효과(판정용): 예선 구성 82.3% → 다시 읽기 규칙 84.3%(+63/−5) → 한국어 인식기 2차 의견 84.7%(+14/−1) → 해석 규칙 4개 86.0%(+39/−2) → 주변 재탐지·확대 재시도·파인튜닝 재시도 86.9%(+25/−1) → 시간 여유를 위해 한국어 인식기를 끈 최종 구성 86.7%.

### 4-3. 오류 사례 분석 및 개선 과정

**오답을 '정답이 어느 단계에서 사라졌는가'로 진단했다.** (예선 구성, 3,352장 중 오답 603장. 단계별 개수는 전체에서 셌고, 규칙 도출과 채택 판정은 봉인 500장을 뺀 2,852장에서 했다)

| 단계 | 장수 | 본선 처방 | 결과 |
| --- | --- | --- | --- |
| 선택 실패: 후보에 정답이 있는데 다른 것을 고름 | 19 | 구분자 일치 규칙 | +10/−0 |
| 다시 읽기가 맞던 답을 덮어씀 | 111 | 1차 후보를 지우지 못하게 함 | +53/−5 |

**오답의 방향.** 서비스에서는 어느 쪽으로 틀렸는지가 중요하다. 늦게 읽으면 남은 날이 실제보다 많게 표시된다.

| 이르게 읽음 | 남은 날이 적게 표시 | 5.3% | 15.8% |

이르게·늦게 읽은 비율은 라벨이 완전한 날짜인 사진(474장, 368장) 기준이다. 이르게 읽은 값의 중앙값은 약 1년으로, 병기 제품에서 제조일을 읽은 경우다.

| 기각한 실험 | 결과 | 배운 것 |
| --- | --- | --- |

규칙으로 닿는 오답은 거의 다 썼다. 남은 것은 인식 품질(도트·각인)과 저해상도다.

## 5. 속도·비용 검증

### 5-1. CPU 추론 속도 측정

개발 PC 두 대에서 연산 스레드를 4개로 제한해 쟀다. 코어를 묶지는 않았고, 느린 쪽 값을 기준으로 본다. 2.7초는 단계별 측정(3.0초)에서 한국어 단계를 뺀 환산값이다.

| 구성 | 장당 | 500장 | 한도 대비 |
| --- | --- | --- | --- |
| EasyOCR 탐지기를 쓴 구성 | 5.8초 | 2,905초 | 초과 |
| 예선 제출본 | 3.2초 | 1,595초 | 64% |
| **본선 최종 구성** (개발 PC 1 / 2) | **2.7초 / 4.0초** | 1,370 / 1,985초 | 55% / 79% |
| 한국어 인식기를 켜면 (개발 PC 2) | 4.7초 | 2,350초 | 94% → 끔 |

사진의 88% 는 장당 1.8초에 끝나고 재시도까지 간 12% 가 시간의 절반을 쓴다. 단계별로는 1차 읽기 40%, 도트 전처리 재시도 23%, 파인튜닝 재시도 11% 순이다(한국어 단계를 켠 측정).

### 5-2. 속도 및 오탐 최적화 전략

| 전략 | 효과 |
| --- | --- |
| 경량 모델로 교체 | 5.8 → 1.8초 |
| 완전한 날짜를 찾으면 잔글씨 생략 | 영양성분표 인식 생략 |
| 탐지는 한 번, 다시 읽기는 잘라낸 조각만 | 탐지가 비용의 대부분 |
| 재시도는 못 읽은 사진에만 | 평균 약 +1초 |
| 시간 예산 가드 | 최근 20장 속도로 총 소요를 예측해 단계를 줄임 |

**시간 예산 가드는 실제로 한 번 발동했다.** 폰 사진 389장을 돌리던 중 PC 가 절전에 들어가 한 장이 2.8시간으로 잡혔고, 가드가 재시도를 생략해 결과 파일 389행을 끝까지 만들었다. 같은 222장에서 재시도를 생략하면 101장, 하지 않으면 130장을 맞혔다. 오탐은 신뢰 등급·긴 숫자열 제거·연도 범위로 억제한다(답한 것의 정밀도 88.9%).

### 5-3. 학습 자원 사용 내역

인식기 파인튜닝(393장, 30 epoch)은 무료 Colab T4 에서 약 1.5시간 걸렸다. 기각한 학습 두 번도 같은 환경이다. 추론과 측정은 개발 PC CPU 로 했다. **유료 GPU 와 클라우드는 쓰지 않았고 비용은 0원이다.**

## 6. 도메인 활용 및 운영 기획

### 6-1. 적용 도메인 및 도입 대상 기업/산업 정의

**중고거래 플랫폼의 식품·건강기능식품 게시글.**

| 항목 | 내용 |
| --- | --- |
| 문제 | 소비기한은 판매자가 손으로 적는다. 약사 단체 모니터링에서 적발된 위반 375건 중 가장 많은 유형이 '사용기한 확인 불가·불일치'(211건)였다 (보도, 매체 간 내역 차이 있음) |
| 규모 | 건강기능식품 개인 간 거래 게시글 482,675건, 위반 조치 14,729건(3.05%), 그중 소비기한 미준수 725건 (2024-05 ~ 2025-12, 식약처 자료) |
| 지금의 처리 | 게시 뒤에 모니터링과 신고로 삭제. 플랫폼이 사진을 OCR 로 읽는다는 보도는 인증마크 확인 용도였고, 소비기한을 읽는다는 자료는 찾지 못했다 |
| 선례 | 일본 메루카리는 소비기한 인쇄 부분의 사진을 필수로 요구한다. 자동으로 읽는다는 자료는 찾지 못했다 |
| 1차 대상 | 위반 통계가 공개된 건강기능식품 카테고리. 거래 조건은 미개봉, 소비기한 이내, 연 10회 이하 |
| 하지 않는 것 | 사기 방지, 개봉 여부 판별. 스티커를 붙이거나 다른 상품을 찍으면 막지 못한다 |

이 시스템은 속이려는 소수를 잡는 장치가 아니다. 날짜를 확인하지 않고 올리는 다수를 게시 전에 돕고, 속이려는 소수는 기존 사후 모니터링이 맡는다.

| 모델 결과 | 판매자에게 일어나는 일 | 남는 위험 |
| --- | --- | --- |
| 맞게 읽음 | 채워진 날짜를 확인 | 없음 |
| 미인식, 확신이 낮음 | 빈칸. 손으로 입력 | 지금과 같음 |
| 이르게 읽음 | 날짜 확대본을 보고 고침 | 안 고치면 판매자에게 불리 |
| 늦게 읽음 | 날짜 확대본을 보고 고침 | **안 고치면 남은 날이 많게 표시** |

판매자가 마지막에 확인하므로 모델의 실수는 대부분 수정 한 번으로 끝난다. 모델을 사람의 판독 정확도와 비교하지 않는다.

### 6-2. 운영 아키텍처 설계 (서버 / 온디바이스)

플랫폼 서버에서 추론한다. 모델 21MB, CPU 전용이다. 폰 안에서 도는 방식은 해 보지 않아 다음 단계로 둔다.

```
날짜면 촬영 (해상도·흐림 검사) → 서버 판독 (10초 제한)
 → 확신도가 기준 이상이고 완전한 날짜면 소비기한 칸 자동 입력, 아니면 빈칸
 → 판매자가 날짜 확대본을 보며 확인 또는 수정
 → 게시글에 "판매자 사진에서 읽은 날짜 · 남은 일수 · 날짜면 원본" 표시
기록: 원본 사진, 촬영 시각, 판독값, 확신도, 판매자 수정 이력, 모델 버전
```

| 자동 입력 기준 (폰 사진 389장) | 채워지는 비율 | 채운 값의 정확도 | 틀린 값을 받는 판매자 |
| --- | --- | --- | --- |
| 기준 없음 | 70.2% | 70.3% | 20.8% |
| **확신도 0.7 이상** | **44.7%** | **77.0%** | **10.3%** |
| 확신도 0.9 이상 | 16.5% | 87.5% | 2.1% |

| 설계 | 이유 (측정값) |
| --- | --- |
| 확신도 기준은 0.7 | 기준 없음 → 0.7 은 틀린 값 41장을 피하려 맞는 값 58장을 포기(1.4 대 1), 0.7 → 0.9 는 32장을 피하려 78장을 포기(2.4 대 1). 틀린 값 하나의 비용이 맞는 값 하나의 이득의 1.4 ~ 2.4배일 때 0.7 이 맞다 |
| 확신이 낮은 판독값은 보여 주지 않고, 판매자 입력과 대조 | 채워 준 값을 같은 사람이 확인하는 것만으로는 검증이 아니다. 판매자가 먼저 입력한 값이 판독값과 다르면 확대본을 보여 준다 |
| 날짜 확대본, 최대 기한 검사 | 확신도만으로는 위험한 오류가 걸러지지 않는다. 늦게 읽은 18장 중 13장이 확신도 0.7 이상. 최대 기한 검사는 크게 늦은 값만 막는 보조 장치이고 효과는 재지 못했다 |
| 10초 안에 답이 없으면 빈칸 | 폰 사진의 32% 가 10초를 넘겼고 그 123장 중 맞힌 것은 13장. 제한을 걸면 자동 입력 44.7 → 40.6%, 틀린 값 10.3 → 8.2% |
| 판독값만으로 자동 차단하지 않음 | 기한이 남은 글의 11.2% 가 지난 것으로 읽힌다 `[가정]`. 판정은 판매자가 확인한 날짜로 |
| 판매자가 값을 고치면 한 번 더 확인 | 판독값과 입력값을 둘 다 기록. 수정의 대부분은 오독을 바로잡은 것이라 제재하지 않음 |
| '확인됨' 대신 판독값과 원본 표시 | 보증 표시는 조작된 날짜에 신뢰를 빌려준다 |
| 선물세트는 상품별로 촬영 | 세트는 가장 이른 날짜가 중요한데 우리 규칙은 한 사진에서 가장 늦은 날짜를 고른다 |
| 판매자 수정값을 검수 후 학습에 사용 | 사람이 입력한 값도 틀린다 (2-2절). 수정값에는 글자 위치가 없어 학습용 글자 조각을 따로 확보해야 한다 |

### 6-4. 비즈니스 손실 절감 효과 및 ROI 기획

**편익을 OCR 이 있어야 되는 것과 아닌 것으로 나눴다.**

| 가치 | OCR 이 있어야 하나 | 근거 |
| --- | --- | --- |
| 입력값과 사진의 대조 | 예 | 판매자가 손으로 넣거나 고친 값이 틀렸을 때, 그 값이 판독값과 우연히 같아 지나갈 확률은 봉인 500장 평균 0.2%, 폰 사진 0.4%. 틀리게 채워진 값을 판매자가 그대로 둔 경우는 이 대조로 잡지 못하고 날짜 확대본과 최대 기한 검사가 맡는다 |
| 날짜면이 찍혔는지 확인 | 예 | 메루카리는 이 확인을 사람이 한다 |
| 입력 편의, 라벨 축적 | 예 | 폰 사진의 41 ~ 45% 자동 입력 (10초 제한을 걸면 41%) |
| 남은 일수 표시, 기한 지난 글 자동 숨김 | 아니오 | 날짜 칸만으로 가능. OCR 의 편익으로 세지 않았다 |

**인력 절감으로는 가치를 설명하지 않는다.** 금액으로 말할 수 있는 편익은 위반 게시글의 사후 처리비인데, 계산하면 본전이 되지 않는다.

| 조건 | 연간 소비기한 위반 | 게시 전에 걸러지는 비율 | 연간 서버 비용 | 손익분기 1건당 처리비 |
| --- | --- | --- | --- | --- |
| 20개월 평균 (옛 6개월 조건 포함) | 435건 | 50% `[가정]` | 17만 원 | 약 780원 |
| 조건 완화 뒤 추정 | 약 180건 | 50% `[가정]` | 17만 원 | 약 1,900원 |

사람이 30초에 검토하는 비용은 약 86원이다 `[가정]`. 손익분기 처리비는 이보다 9 ~ 22배 크다. 개발과 앱 화면 변경 비용, 판매자가 사진을 한 장 더 찍는 부담도 여기에 들어 있지 않다.

**플랫폼이 도입할 이유는 비용 절감이 아니라 규제 대응이다.** 건강기능식품 개인 간 거래는 시범사업이고, 국회에서 모니터링 인력이 5명이라는 지적을 받았으며 거래를 금지하는 법안이 계류 중이다(보도). 게시글마다 날짜면 사진과 판독 기록이 남는 것은 관리 체계의 증거가 된다. 이 가치는 금액으로 재지 못했다.

| 채점 서버 속도 미실측 | 개발 PC 기준 한도의 55 ~ 79% | 시간 예산 가드로 완주 보장 |
| 봉인 500장 | 완전 무오염은 아님 | 예선 때 오답을 보고 라벨 7장을 고쳤다. 본선 판정은 전부 나머지 2,852장에서 |
| 조작, 개봉 여부, 카테고리를 바꿔 촬영을 피함 | 막지 못함 | 범위 밖으로 명시. 원본과 수정 이력 보존 |
| 판매자가 보지 않고 확인을 누름 | 미측정. 늦게 읽은 값 3.3% 중 그대로 게시되는 비율을 모른다 | 확인을 버튼이 아니라 일(日) 칸 재입력 같은 동작으로. 실제 수정 비율을 지표로 |
| 소비기한 위반은 적다 | 게시글의 약 0.15% | 단속이 아니라 정보 제공을 목적으로 둠 |
| 제도가 바뀔 수 있음 | 시범사업, 종료 시한 미공개 | 기한 지난 식품은 플랫폼 규칙으로도 금지라 가공식품에 같은 설계 적용 |
| 근거 수치 | 보도와 공개 통계. 플랫폼 내부 자료 없음 | 가공식품 게시글 수는 공개 자료가 없음 |

**다른 현장과의 연결**: 뼈대는 '읽은 값을 기준값과 대조하고 예외만 사람에게 넘긴다'이다. 출하 표시물 검증에서는 기준값이 품목 마스터, 여기서는 판매자 입력이다. 기록 항목(원본·판독값·수정 이력·모델 버전)은 감사 추적이고, 4-2 의 채택 기준과 봉인 500장은 모델을 바꿀 때의 재검증 기준이다.

**확장**: 건강기능식품 → 가공식품·명절 선물세트 → 지금은 지우는 품목보고번호를 읽어 회수 대상 확인. 같은 파이프라인은 식품공장의 출하 전 날짜 인쇄 확인에도 쓸 수 있다. 공장은 정답(제조일 + 품목별 소비기한 일수)을 알아 대조만 하면 되고, 기대값을 어긋나게 넣은 실험에서 오인쇄를 놓칠 확률은 한 장당 평균 0.2% 였다.
