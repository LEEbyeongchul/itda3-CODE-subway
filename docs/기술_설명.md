## 1. 한 줄 요약

**PaddleOCR PP-OCRv5 mobile 탐지기 + 영문 인식기(둘 다 사전학습 그대로) + 우리 도메인 규칙 후처리.** 측정용 500장에서 **73.6%**, 4코어 CPU 장당 **1.8초**(500장 약 900초, 한도 2,400초). 학습(파인튜닝)은 아직 하지 않았다.

## 3. 파이프라인

```
원본 이미지
 ├─ ⓪ EXIF 회전 보정. JPEG 은 디코딩 단계에서 긴 변 2000px 이하로 축소 (24MP 원본 디코딩 비용 절감)
 ├─ ① 1패스: 긴 변 640px 축소본
 │     ├─ 탐지  PP-OCRv5_mobile_det (약 5MB)       텍스트 박스. 640px 기준 4스레드 약 300ms
 │     ├─ 인식  en_PP-OCRv5_mobile_rec (약 8MB)    박스를 글자 크기 내림차순으로 8개씩 배치 인식.
 │     │                                           연도 포함 날짜를 찾으면 그 글자 높이의 60% 미만 박스는 건너뜀 (영양성분표 잔글씨 생략)
 │     └─ 후보 없으면 1024px 로 한 번 더 (어려운 장에만 비용을 더 씀)
 ├─ ② 2패스: 후보 줄의 단어 박스만 원본 해상도에서 크롭해 재인식 (검출기 재실행 없음)
 ├─ ③ 후처리 (4절)
 └─ ④ 출력  YYYY-MM-DD / NONE-MM-DD / YYYY-MM-NONE / NONE
```

- 인식 결과에서 허용 문자(숫자, 영문, `. / - :` 공백) 밖의 글자는 공백으로 바꾼다. 삭제하면 `2021(3)` → `20213` 처럼 숫자가 붙는다.
- EasyOCR 은 `ITDA_DET=craft`, `ITDA_REC=easyocr` 로 비교용으로만 남아 있다.

## 4. 후처리 규칙 (요약. 정본은 `날짜_해석_규칙.md`)

1. **오독 복원.** 영문자를 허용하면 숫자가 O/I/S/B 로 읽힌다 → 숫자에 인접한 혼동 글자를 숫자로 (`2O27` → `2027`), `0ct` → `Oct`, 구분자 사이에 홀로 낀 글자 제거 (`2020. J .11.04`).
2. **정규식 4단계.** 상위 단계에서 후보가 나오면 하위는 보지 않는다.
   - 1단계 완전한 날짜: `YYYY.MM.DD`, `YYYYMMDD`, `DD.MM.YYYY`(연도가 뒤면 일/월/년), `YY.MM.DD`, 영문 월(`FEB/26/21`, `04-Jul-21`, `DEC-28-2021`), 구분자 하나 빠진 `27.102023`
   - 2단계 공백 구분 `30 12 23`(일/월/년 우선), 6자리 압축 `250626`
   - 3단계 연·월만: `2027.7`, `12.2020`, `25.11`, `NOV 2021`, `EXP:08/22 MFD:08/20`(월/연도 병기)
   - 4단계 월·일만: `10.14` → `NONE-10-14`
3. **2자리 연도 3숫자**(`26.06.25`): 년/월/일 우선. 년/월/일이 무효이거나, 그 연도가 2028 이상이면서 일/월/년도 성립하거나, 이미지에 `BBD`·`BEST BEFORE`·`EXP`·`USE BY`·`DD/MM` 키워드가 있으면 일/월/년.
4. **검증.** 연도 2017~2031, 월 1~12, 일 1~31. 9자리 이상 숫자열(품목보고번호, 바코드)은 파싱 전에 제거.
5. **선택.** 후보가 여럿이면 **패턴 신뢰 등급이 가장 높은 것들끼리** 가장 늦은 날짜(운영진 확정 규칙). 등급을 두기 전에는 영양성분표 숫자열이 2단계 패턴으로 잡혀 진짜 날짜를 밀어내는 경우가 500장 중 15장 있었다.

## 5. 측정 방법

- **라벨.** 팀이 직접 3,352장 중 1,303장에 날짜·원문 형식·태그(흐림 b, 작음 t, 각인 e, 일먼저 d, 날짜 2개+ 2)를 붙였다. 해상도 층(small/mid/large)을 섞어 무작위 추출.
- **측정용 vs 튜닝용 분리.** 블록 1~5(500장)는 측정 전용으로 어떤 튜닝·학습에도 쓰지 않는다. 블록 6 이후(803장)는 튜닝·학습용. "안 본 데이터에서 X%"를 말하기 위한 분리.
- **정답 기준.** `final_date` 완전 일치. `NONE`, `NONE-MM-DD`, `YYYY-MM-NONE` 도 정답 값.
- **도구.** `notebooks/eval.py --pred submission.csv --blocks 1-5`. 블록·형식·태그·해상도별 정확도와 오답 유형(미검출 / 전부 틀림 / 월일 틀림 / 연도만 틀림)을 낸다.
- **속도.** 채점 서버(4코어)를 `psutil.cpu_affinity([0,1,2,3])` + `ITDA_THREADS=4` 로 흉내 내 측정.
- **채택 기준.** 튜닝셋(블록 6·9·10, 300장)에서 실험 → 500장에서 회복·퇴보 수를 따로 세어 확인. 300장 기준 ±1%p 는 잡음(표준오차 약 2.6%p)이라 채택 근거로 쓰지 않는다. 규칙 버그 수정은 문턱이 낮고 임계값 튜닝은 높다.

| 단계 | 바뀐 것 | 133장 | 500장 | 4코어 장당 |
| --- | --- | --- | --- | --- |
| 원래 | EasyOCR CRAFT + english_g2 | 39.1% | | 약 5초 |
| 규칙 5개 수정 | 연도 하한, 영문 월, MM.YYYY, YYYY.MM, 일먼저 힌트 | 44.4% | | |
| 인식기 교체 | english_g2 → PP-OCRv5 rec (v3 53.4%, v4 58.6% 비교 후) | 60.9% | | 5.81초 (한도 초과) |

## 8. 왜 이렇게 결정했나

- **YOLO 3단계 탐지 대신 사전학습 Paddle 탐지기.** 박스 라벨이 0장이었고, 탐지기 교체만으로 속도 한도와 정확도가 동시에 해결됐다. 남은 오답이 "엉뚱한 숫자열 오탐"이면 Full 탐지를 재검토하지만, 신뢰 등급 도입 후 그 비중은 작다.
- **PP-OCRv5 mobile.** v3/v4/v5 를 같은 조건에서 비교해 v5 가 가장 높았고 속도는 셋 다 호출당 70ms 안팎.
- **CRAFT 포기.** 4코어에서 500장 2,905초로 셀 타임아웃(2,400초)을 넘겼다. 초과하면 CSV 가 안 나와 정확도까지 0점.
- **NONE 정책.** 후보가 없으면 `NONE`. `NONE` 이 정답 값으로 존재(연도 없음 2.5%, 일 없음 3.3%)하고, 사전확률 날짜를 찍는 것보다 기대값이 낮지 않다.

## 9. 재현과 제약

- `bash download_weights.sh` → `ITDA_INPUT_DIR=<폴더> ITDA_OUTPUT_PATH=<csv> jupyter nbconvert --to notebook --execute predict.ipynb`
- 가중치는 git 에 없다(규정). PaddleOCR 공식 사전학습 모델을 스크립트가 받아 `weights/` 에 둔다. 파인튜닝 모델이 생기면 배포 위치를 스크립트에 추가한다.
- 오프라인: 모델 캐시를 숨기고 모든 HTTP 를 죽은 프록시로 보낸 상태에서 완주 확인. Linux 에서 `libGL` 이 없으면 비headless OpenCV 가 import 에 실패하므로 headless 예비본을 `weights/cv2_headless` 에 두고 자동 대체한다.
- Python 3.10 의존성은 Windows·Linux 드라이런으로 해결 확인. 실제 Linux 실행은 `.github/workflows/smoke.yml` 이 push 마다 검증한다.
