## 1. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 한 줄 요약 | 판매자가 소비기한 면을 찍으면 OCR이 날짜를 읽어 자동 입력하고, 그 값으로 잔여기한 라벨·정렬·임박 알림을 제공 |
| 겉으로 보이는 목표 | 소비기한을 **거래 정보**로 활용 (라벨링, 검색·정렬, 알림) |
| OCR의 역할 | 그 정보가 판매자 말이 아니라 **사진에서 읽은 값**이 되게 하는 것 |
| 이전 안과의 차이 | 게시 흐름(촬영 → OCR 판독)은 거의 같음. **초점**이 "부정 게시물 단속"에서 "신뢰할 수 있는 정보 제공"으로 이동 |

---

## 2. 방향 전환: 어디서 어디로 바뀌었나

**원래 안 (단속 중심)**

1. 판매자가 사진도 올리고 날짜도 직접 입력
2. OCR이 사진에서 날짜 추출
3. 입력값과 비교해 차이 나는 것만 사람이 검토

→ 목적: 거짓 소비기한 게시물 적발

**바뀐 안 (정보 활용 중심)**

- 부정 게시물을 잡는 것보다, **제대로 입력된 소비기한을 쓸모 있는 정보로 만드는 것**에 집중
- 소비기한 · 남은 일수 라벨 자동 부착
- 구매자는 잔여일 기준으로 검색 · 정렬
- 안 팔린 채 기한이 임박하면 판매자에게 알림

**왜 바꿨나**

- 단속 중심 안은 "실제로 거짓 게시물이 얼마나 되는지" 근거가 없어서 문제 제기가 약했음
- 정보 활용 안은 판매자·구매자 모두에게 눈에 보이는 이득이 있음

---

## 3. 문제 상황 정의

**전제로 알아둘 것**

- 현재도 소비기한 **입력은 의무** (소비기한이 있는 가공식품만 거래 가능하기 때문)
- 즉 날짜 데이터 자체는 이미 쌓이고 있음

**그런데도 남는 문제**

| 대상 | 문제 |
|---|---|
| 판매자 | 글을 올려 두고 방치하면 기한이 다가오는지 알기 어려움 |
| 구매자 | 여러 게시물의 남은 기한을 한눈에 비교하거나 정렬할 수 없음 |
| 플랫폼 | 입력된 날짜가 **판매자 자기보고 값**이라, 이를 라벨·정렬 같은 공식 정보로 내세우기엔 신뢰 근거가 없음 |

> ⚠️ 논의 중 계속 나온 반박: "판매자·구매자 문제는 기존 입력 데이터만으로도 해결되는 거 아니야?"
> → 맞음. 그래서 **OCR이 필요한 이유는 세 번째 줄(자기보고 값의 신뢰 문제)** 에서 나옴. 자세한 건 5장.

---

## 4. 활용 목표 및 기대효과

| 기능 | 기대효과 |
|---|---|
| 잔여기한 자동 라벨 (예: "D-12") | 구매자가 게시글만 봐도 신선도 파악 |
| 잔여일 기준 검색 · 정렬 · 필터 | 구매자가 원하는 조건의 상품을 빠르게 찾음 |
| 기한 임박 시 판매자 알림 | 판매자는 가격 조정·재홍보 타이밍을 놓치지 않음 |
| 기한 지난 게시물 자동 숨김 | 기한 지난 식품이 노출되는 상황 방지 |
| 운영자 대시보드 | 자동 입력이 잘 되고 있는지 한 화면에서 확인 |

> 기대효과는 모두 **정성적**으로만 서술. 판매 속도 개선 등 수치 효과는 근거가 없으므로 보고서에 숫자로 쓰지 않기.

## 5. 핵심 쟁점 — 왜 꼭 OCR이어야 하는가

가장 오래 고민한 부분. "라벨·알림은 좋은데, 그걸 굳이 OCR로 해야 해?"

### 5-1. 검토했다가 탈락시킨 근거

| 근거 | 탈락 이유 |
|---|---|
| 날짜 데이터가 없어서 | 이미 입력 의무라 데이터는 있음 |
| 사람 입력 실수를 줄여줌 | 실수가 실제로 많은지 근거 없음 + 우리 모델도 정확도 100%가 아님. "사람보다 정확하다"는 비교는 자기모순 위험 |
| 사진이 기록으로 남아 구매자가 믿을 수 있음 | "소비기한 사진 필수 업로드"만 해도 됨. OCR이 꼭 필요하진 않음 |
| 데이터 정리가 수월해짐 | 입력 데이터만 있어도 정리 가능. OCR 고유 장점 아님 |
| 판매자 수정값이 학습 데이터가 됨 | OCR의 **부가 장점**일 뿐, OCR을 써야 하는 이유는 아님 |
| 판매자는 확인 버튼만 누르면 됨 | 포장지를 보고 옮겨 적는 것이라 회상이 아님. 남는 건 타이핑 vs 버튼 정도의 편의성 (자세한 내용은 5-3) |

### 5-2. 최종 결론

> **정보 서비스(라벨·정렬·알림)가 겉으로 드러나는 목표이고,
> OCR 판독은 그 정보가 믿을 만해지기 위한 전제조건이다.**

- OCR 없이 라벨을 붙이면, 그 라벨은 "판매자가 적은 값이 맞다"는 **검증되지 않은 가정** 위에서만 의미가 있음
- OCR이 사진에서 날짜를 읽으면, 라벨의 출처가 **판매자의 말 → 제품에 인쇄된 날짜**로 바뀜
- 따라서 "단속"과 "정보 활용"은 서로 다른 목적이 아니라 **같은 흐름의 앞뒤**
  - 앞: 사진에서 읽은 값으로 입력 (신뢰 확보)
  - 뒤: 그 값을 정보로 활용 (서비스)
- 발표할 때는 "단속"이라는 표현 대신 **"정보의 출처를 사진으로 바꾼다"** 로 설명하면 초점이 흐려지지 않음

### 5-3. 그 밖의 근거 (보조적)

OCR이 필요한 핵심 이유는 **5-2 하나**이고, 아래는 그 논리를 보조하는 정도임.

1. **운영자가 판독 현황을 통계로 볼 수 있다**
   - 판독 실패율, 판매자 수정 빈도 등을 한 화면에서 확인
   - ⚠️ 이게 다시 "검거"처럼 보일 수 있다는 우려 있음 → 8장 참고

**근거로 쓰지 않기로 한 것: "판매자는 확인만 하면 된다"**

- 판매자는 포장지를 눈으로 보고 옮겨 적는 것이므로 "떠올려서 입력"이 아님 → 재인이 회상보다 쉽다는 논리가 적용되지 않음
- 남는 차이는 타이핑 → 버튼 한 번 수준의 편의성인데, 이는 5-1에서 탈락시킨 "입력 편의성"과 같은 이유
- 오히려 값을 제대로 안 보고 확인만 누르는 **자동화 편향** 위험이 있음 (7장 한계와 연결)
- 다만 입력칸이 OCR 값으로 미리 채워지면 판매자가 건드리지 않은 게시글의 날짜는 사진에서 나온 값이 됨 → 이건 편의성이 아니라 **값의 출처** 문제이므로 5-2 결론에 이미 포함됨

## 6. 최종 게시 플로우 (5단계)

```
① 촬영      판매자가 소비기한이 나온 면을 사진으로 찍음
   ↓
② 판독      OCR이 날짜를 읽어 입력칸에 자동으로 띄움
            (못 읽으면 빈칸 → 판매자가 직접 입력)
   ↓
③ 확인      맞으면 [확인] 버튼 / 틀리면 판매자가 직접 수정
   ↓
④ 게시      소비기한 · 잔여일 라벨이 붙은 채로 판매글 등록
   ↓
⑤ 모니터링  운영자가 통계 대시보드에서 판독 결과 확인
```

**모델 범위와 맞는지 체크**

- 사진 1장 입력 → 날짜 판독: 우리 모델 범위와 일치
- 연/월/일을 각각 못 읽으면 NONE 처리 → ②의 "빈칸" 동작과 연결
- 바코드·QR 판독 기능은 없음 → 플로우에 넣지 않기

## 7. 남은 한계 — 고의적 사후 수정

### 문제

- 정보로 쓰이는 순간, 판매자는 **기한을 실제보다 길게 부풀릴 동기**가 생김
- ③ 단계에서 OCR 값이 맞는데도 일부러 다른 날짜로 수정하면, **게시 시점에는 걸러낼 방법이 없음**
- 순수하게 오판독을 고친 사람과 고의로 부풀린 사람을 구분할 수 없음

### "구매자가 사진 보고 직접 비교하면 되지 않나?" → 부적절

- 구매자가 매번 사진을 확인해야 한다면 **자동 라벨을 붙이는 의미가 사라짐**
- 오히려 라벨이 "확인된 정보"처럼 보여서 **거짓 신뢰**를 줄 위험 (표시가 위조에 신뢰를 빌려주는 구조)

### 보완 방안 2가지

| # | 방안 | 내용 |
|---|---|---|
| 1 | 라벨 신뢰도 구분 | 수정 없이 확인된 글과 수정된 글의 라벨 표시를 다르게 |
| 2 | 수정 패턴 모니터링 | 대시보드에서 특정 판매자의 반복 수정 등 패턴 확인 |

## 8. 팀 논의 필요 사항

- [ ] **5-2 최종 결론에 동의하는지**
  "OCR 판독은 정보 서비스의 전제조건"이라는 설명으로 발표 논리를 잡을지

- [ ] **"사람 입력 실수 감소"를 보고서에 넣을지**
  넣는다면 "사람보다 정확하다"가 아니라 가정 기반 비교로만, 가정임을 명시해서

- [ ] **운영자 대시보드 지표를 어디까지 보여줄지**
  판독 실패율·수정 빈도를 넣되, "검거 도구"가 아니라 "자동 입력 품질 관리"로 보이게 표현하는 방법
