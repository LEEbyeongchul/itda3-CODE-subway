## 2. 현재 파이프라인 (`predict.ipynb`)

```
EXIF 보정 → 640px 축소 (후보 없으면 1024px 재시도)
 → PP-OCRv5 mobile det 탐지 (5MB, oneDNN 끔)
 → PP-OCRv5 mobile rec(en) 인식, 글자 크기순 8개씩 배치, 연도 포함 날짜 찾으면 작은 박스 건너뜀
 → 2패스: 후보 줄만 원본(≤2000px)에서 크롭해 재인식
 → 후처리: 오독 복원(2O27→2027, 0ct→Oct) → 정규식 4단계 → 연도 2017~2031 검증 → 가장 늦은 날짜
 → YYYY-MM-DD / NONE-MM-DD / YYYY-MM-NONE / NONE
```

- 후처리 규칙은 `docs/날짜_해석_규칙.md` 가 정본. 라벨링 도구 `notebooks/label.py` 와 파서가 같은 규칙. **운영진이 "모호한 값은 팀 후처리 규칙으로 채점"이라 확정했으므로 요약서 2p 에 이 규칙 표를 반드시 넣는다.**
- 환경변수: `ITDA_DET=craft`, `ITDA_REC=easyocr` 로 예전 EasyOCR 구성과 비교. `ITDA_THREADS=4` 로 스레드 제한. `ITDA_DEBUG=1` 로 장별 OCR 텍스트·후보 출력.
- 가중치는 `weights/` 에서만 오프라인 로드. `bash download_weights.sh` 로 받는다 (EasyOCR 2개 + Paddle 탐지·인식 폴더 2개).

## 5. 다음 작업 (우선순위 순)

### A. 해상도 사다리 실험 — 9/10 오후 완료. **결론: 해상도를 올려도 정확도가 안 오른다.**

튜닝용 300장(블록 6·9·10), 14코어 PC. `ITDA_LADDER`, `ITDA_DET_LIMIT`(탐지 리사이즈 상한, 0이면 모델 기본 resize_long 960), `ITDA_BOX_THRESH` 로 실험.

| 구성 | 정확도 | 300장 시간 |
| --- | --- | --- |
| c0 기본 640→1024 (구 파서) | 70.0% | 591s |
| c1 960→1600 | 70.3% | 779s |
| c2 기본 + box_thresh 0.4 | 71.0% | 758s |
| c3 640→1024→1600 | 70.0% | 877s |
| c4 800→1280 | 71.0% | 864s |

- 차이가 전부 ±1%p 로 잡음 수준인데 시간은 30~50% 늘어난다. **미검출은 해상도 문제가 아니라 인식기가 못 읽는 문제.** → D(파인튜닝)가 정답.
- **box_thresh 0.4 는 500장에서 기각**: 73.6% → 71.2%, 회복 0 / 퇴보 12, 시간 +13%. 300장의 +1%p 는 잡음이었다. 튜닝셋에서 1%p 차이로 채택하면 안 되는 이유의 실례.
- 주의: c1~c4 는 B 의 새 파서로, c0 는 구 파서로 돌았다. 새 파서 c0 재측정과 500장 갱신은 아래 "결과표" 참고.
- 탐지 모델 기본은 입력을 긴 변 960 으로 항상 리사이즈한다(640 은 확대). 사다리를 바꾸려면 `ITDA_DET_LIMIT` 도 같이 바꿔야 실제 해상도가 달라진다.

### B. 오답 열어 보기 — 9/10 오후 진행, 결과 반영됨

"전부 틀림" 단일 날짜 25장을 `ITDA_DEBUG=1` 로 열어 본 결과:
- **대부분 영양성분표 숫자열 오탐.** `78 7 5 31`, `230121`, `19 07 16` 같은 줄이 공백 구분(SP_*)·6자리 압축(CMP6_*) 패턴에 걸림. 그중 5장은 진짜 날짜도 후보에 있었는데 "가장 늦은 날짜" 규칙이 잡음(연도가 더 큼)을 골랐다.
- **구분자 하나 빠진 오독** 여러 건: `27.102023`, `EXP:18/052021`, `17-072022`, `2021.1105`.
- 구분자가 공백·점 섞임: `17.10 2020 / 17 10. 2021`.

반영한 수정 (predict.ipynb):
1. **패턴 신뢰 등급 `KIND_TIER`.** 완전한 날짜(등급 1) > 공백·6자리(2) > 연월만(3) > 월일만(4). 이미지 안 후보 중 가장 좋은 등급끼리만 "가장 늦은 날짜" 비교.
2. 구분자 하나 빠진 `DD.MMYYYY`, `YYYY.MMDD` 패턴 추가 (4자리 20xx 앵커라 오탐 낮음).
3. `DD.MM.YYYY` 에 공백 구분 허용.

효과: 오답 25장 중 9장 회복. 전체 셋: 튜닝 300장 70.0% → 70.7%, **측정 500장 71.2% → 73.6% (회복 15, 퇴보 3)**. 퇴보 3장은 정답이 연월만(2026.01, 03/2025)인 이미지에서 다른 줄 잡음이 완전한 날짜 형태로 읽혀 등급에서 이긴 경우 — 500장 중 6장뿐인 형식이라 감수. 남은 미검출 75장은 탐지·인식 개선(D) 영역.

### C. 날짜 2개 이상 처리 (51장 중 21장 오답)

"가장 늦은 날짜" 규칙 자체는 맞다. 문제는 둘 중 하나를 못 읽어 나머지를 답하는 것. A·B 가 해결하면 같이 풀린다.

### D. Phase 3 인식기 파인튜닝 — 9/11 진행 중

**데이터 (9/11 15:48 추출 완료, `data/rec_train/`):** 803장 중 547장 채택(정확히 읽힌 292 + hard sample 255). 검수 플래그 105장 제외 → **학습 393 / 검증(블록 6) 49**. `notebooks/prepare_train_lists.py` 가 `train_clean.txt`/`val_clean.txt` 를 만든다. 시트 확인 결과 플래그 크롭은 실제로 `까지`·`EXP` 등 부가 글자, 두 줄, 잘림이었다.

**미검출 원인 분해 (803장, 크롭 편집거리 기준):** 미검출 123장 중 근접 오독(dist≤3) 31, 크게 빗나감(dist 4+) 84, 크롭 없음 1. 즉 미검출의 70% 는 탐지·인식이 날짜 근처에도 못 간 경우라 인식기 파인튜닝만으로는 한계. 반대로 **파이프라인은 틀렸는데 원본 해상도 크롭에서는 정확히 읽힌 이미지가 24장(3%)** 있다 → "후보 없을 때 640px 박스들을 원본 해상도로 재인식" 폴백이 싸게 회복할 여지 (다음 실험 후보 F).

**학습 (로컬 CPU, `notebooks/finetune_cpu.py`):** GPU 없이 이 PC 에서 돌린다. torch 를 paddle 보다 먼저 import 하는 래퍼로 Windows DLL 충돌 회피. **실측 속도: 샘플당 약 2.6초, epoch(393장)당 25분.** 10 epoch 은 4시간이라 3 epoch + warmup 1 로 재시작했고 epoch 2 까지 저장(`train_out/itda_en_rec/iter_epoch_2`), epoch 3 도중 17:05 중단. 학습 중 train acc 6%→20%, loss 28→19 로 내려가는 건 확인. **함정:** PaddleOCR 평가 루프가 Windows 에선 마지막 배치를 버리므로 검증 배치가 1개면 acc 0 으로 나온다 → 드라이버가 평가 배치 8 로 고정. 실제 성능 상승은 Colab GPU 에서 3차 라벨·합성 데이터 포함 30 epoch 돌릴 때 기대.

**CPU 파인튜닝 결과 (9/11 20:55, epoch 2 체크포인트, 393장, 18 iter):** 측정 500장 **73.6% → 74.0%, 회복 25 / 퇴보 23.** 순증 2장은 잡음이고 퇴보 양상이 나쁘다 — `2026.03.11 → 2026-03-01`, `2021.01.28 → 2021-01-02` 처럼 일 자릿수를 떨어뜨림(과소 학습으로 CTC 가 불안정). **채택하지 않음, 사전학습 가중치로 원복.** 결과는 `results/eval500_ft_cpu_epoch2_2026-09-11.csv`. 결론: 파인튜닝 파이프라인(데이터 → 학습 → 내보내기 → 교체 → 측정)은 끝까지 검증됐고, 실제 상승은 GPU 에서 합성 3,000장 + 실제 393장으로 30 epoch 이상 돌려야 기대할 수 있다. Colab 노트북·zip 준비 완료.

**미검출 이미지 직접 확인 (9/11, `results/` 의 miss 분석 + 12장 육안):** 도트매트릭스 잉크젯 인쇄 7~8장, 각인 2장, 아주 작은 글씨 2장. **해상도 문제가 아니라 점 인쇄를 글자로 못 보는 문제.** 대응: (a) 점 이어 붙이기 전처리 폴백 (구현됨, 검증 전), (b) 도트매트릭스 합성 데이터로 인식기 학습 (미작성).

## 6. 함정 목록 (다시 밟지 말 것)

- **Paddle 이 predict 를 부르면 torch 스레드가 1로 떨어진다.** CRAFT 를 쓰면 4배 느려짐. 지금은 CRAFT 를 안 쓰지만 `ITDA_DET=craft` 경로에 재고정 코드가 있다.
- **torch 를 paddle 보다 먼저 import.** 반대면 Windows 에서 DLL 오류.
- **Windows paddle 3.3.1 탐지 모델은 oneDNN 오류** → `enable_mkldnn=False`. Linux 에서도 같은 설정 유지 (안전).
- **paddleocr 설치가 opencv 를 바꾼다.** requirements 는 opencv-python-headless 와 opencv-contrib-python 을 같은 4.10.0.84 로 고정.
- **pip 설치 중 다른 파이썬 프로세스가 cv2 를 잡고 있으면 실패.** 노트북 돌리면서 설치하지 말 것.
- **Bash heredoc 으로 노트북을 패치하면 백슬래시가 뭉개진다.** 패치 스크립트는 파일로 써서 실행.
- **라벨 CSV 는 엑셀로 열지 않는다.** 앞자리 0 이 사라진다.
- 노트북 결과를 볼 때 `nbconvert --execute` 의 stdout 은 파이프 끝에서 한꺼번에 나온다. 진행률을 보려면 출력 노트북 파일을 열거나 `--output` 파일 시각을 본다.
